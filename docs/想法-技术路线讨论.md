# 想法 · 技术路线与落地可行性讨论

> 状态：**讨论中（第 6 轮：冒烟测试完成，口径已实测）**
> 用途：记录逐轮讨论的结论、技术路线候选与可行性判断。
> 纪律：本阶段只讨论「有没有可行路线 / 落地会卡在哪」，**不实施**。
> 责任人：主人定方向，女仆做路线枚举与可行性核查。

---

## 0. 想法一句话描述（第 1 轮已确认）

做一套**给 agent 用**的 EVE Online 配装工具套件，三个能力台阶：

1. **取数**：拿到配装模拟的原始数据；
2. **理解**：把数据转成可判断的语义，给出评价与建议；
3. **生成/修改**：按需求生成配装，或修改现有配装。

工具清单不预设，按需要长。**交付对象是 agent，不是人**（这一点决定了后面所有取舍）。

## 1. 结论速览

| # | 判断 | 依据 |
|---|---|---|
| 1 | 「算得准」已经不是问题，不用自研 dogma 引擎 | 已有 MIT 许可、Win 轮子齐全的 Rust 引擎，含派生指标与配装合法性校验 |
| 2 | 真正的工作量在**语义层**（把几百个属性压成 agent 能吃的几十个指标） | 引擎输出是原始 dogma 属性字典，直接投喂 LLM 会爆上下文 |
| 3 | 真正的不确定性在**判据层**：什么叫「这套配装好」 | SDE 里没有「好」，取决于 PvP/PvE/舰队/单人、预算、技能、对手 |
| 4 | 「生成配装」不是算力问题，是**搜索 + 目标函数**问题 | 组合空间巨大，但有免费的合法性校验做护栏，可控 |
| 5 | 整条链**没有不可行环节**，有 4 个明确工位要自己写 | 见第 4 节 |

**一句话**：这是「胶水 + 判据 + 提示工程」项目，不是「数值复现」项目。数值复现那部分已经被开源做完了。

## 2. 地基核查（2026-10-18 实查）

### 2.1 数据层：官方 SDE，可用且有增量机制

- 官方静态数据导出 SDE，提供 **JSON Lines / YAML** 双格式，有 `latest.jsonl` 取最新 build number、`changes/<build>.jsonl` 取**增量变更**、全资源支持 **ETag / Last-Modified**。([Static Data 文档](https://developers.eveonline.com/docs/services/static-data/))
- → 意味着「数据陈旧」不是不可解问题：可以做到「每日比对 build number，变了才拉增量」。

### 2.2 计算层：eveshipfit dogma-engine（关键发现）

`eveshipfit-dogma-engine` 13.6.0，**MIT 许可**，Rust 内核 + Python/JS/Rust 三套绑定，PyPI 上有 **Windows x86-64 wheel**（abi3，Python ≥3.10 通用），2026-10-06 发布。([PyPI](https://pypi.org/project/eveshipfit-dogma-engine/) / [仓库](https://github.com/EVEShipFit/dogma-engine))

能力清单（已实读 README 确认，非推测）：

- 四趟计算：收集属性 → 收集效果 → 应用效果（含**堆叠惩罚**、技能、热过载、突变/深渊模块、模式、战斗机、指挥脉冲）→ **pass 4 补派生属性**；
- 派生属性（pass 4）覆盖：**EHP（护盾/装甲/结构/总）**、**电容稳定百分比/耗尽时间/峰值**、**DPS（含/不含装填、齐射、Alpha、无人机、战斗机）**、**alignTime**、速度、信号半径、扫描分辨率、锁定距离/目标数、转速、爆炸半径/速度、伤害分布、每件装备的修复/电容传输速率等；
- **配装合法性校验 `validate`**：资源（CPU/PG/标定/无人机带宽与容量/货舱/弹药容量）、槽位与挂点、错槽、槽位占用、子系统冲突、**技能要求**、rig 尺寸、船只限制、同类上限（如双推进器）、弹药组与尺寸 —— 直接产出「游戏里飞不出去」的违规列表；
- **格式互转**：EFT（剪贴板格式）、ESI 配装、ESI 击杀邮件、DNA 链接、EVEShip.fit 链接、esf/1；读也写；
- **`incoming` / `outgoing` 联动**：一套配装的输出可作另一套的输入 → 舰队 buff、指挥脉冲、被网/被反跳等外部效果可建模；
- **线程安全**：除加载 SDE 外全部释放 GIL，可线程池并行算。

配套 `eveshipfit-sde`（PyPI/npm）：把官方 SDE 压成 `sde.dat`（FlatBuffers），**每日 12:00 UTC 自动对最新 SDE 重建**，变了就发版。([sde-patched](https://github.com/EVEShipFit/sde-patched))

本地环境已具备：Python 3.14.4 / uv 0.9.18 / Node 24.12（abi3 wheel 在 3.14 可用；WASM 变体也可走 Node）。

### 2.3 备选计算层：pyfa

`pyfa-org/Pyfa` 仍在活跃维护（最新 v2.69.3，2026-10-17 发布）。Python 实现，功能最全，但 **GPL-3**、引擎与 GUI 耦合、依赖自带数据库、要自己包一层。([仓库](https://github.com/pyfa-org/Pyfa))

→ 定位：**只作为「对数字」的裁判**（拿它的结果做回归基线），不作为主引擎。

### 2.4 已有同类工具（避免重复造轮子）

- [`eve-sde-mcp`](https://github.com/ramonvanalteren/eve-sde-mcp)：MCP 形式的 SDE 查询（船/模块/蓝图）。
- [`EOE_MCP`](https://github.com/Berman510/EOE_MCP)：MCP 形式的 ESI 封装。

→ 这些停在「查数据」。**没有人做「算指标 + 评优 + 生成」的闭环**，这就是本项目的生态位。

### 2.5 维护风险信号

- ESI 在持续清理旧路由（[2026-03-24 移除 legacy routes](https://developers.eveonline.com/blog/spring-cleaning-legacy-routes-removed-24-march-2026)）→ 任何依赖 ESI 的部分都要把接口面收窄、做好降级。
- 结论：**尽量只依赖「SDE + 本地引擎」**，把 ESI 限定为可选增强（读自己账号数据用）。

## 3. 技术路线候选

| 层 | 路线 | 核心依赖 | 关键卡点 | 维护成本 | 初判 |
|---|---|---|---|---|---|
| L0 数据 | A. 官方 SDE 直读 | 官方 JSONL/YAML | 解析器要自己写；无计算 | 低 | 可行，但没必要单独走 |
| L0 数据 | **B. eveshipfit-sde** | `pip install eveshipfit-sde` | 上游每日重建，跟随即可 | 极低 | **推荐** |
| L1 计算 | C. 自研 dogma 引擎 | 无 | 堆叠惩罚顺序、被动回充、热过载、突变、无人机/战斗机、技能矩阵…… | 极高，且必然算错 | **不可行**（性价比灾难） |
| L1 计算 | D. 包 pyfa 的 eos | pyfa + 自建数据库 | GPL-3 传染、GUI 耦合、胶水厚、版本跟随 | 中高 | 有条件可行，仅作裁判 |
| L1 计算 | **E. eveshipfit-dogma-engine** | Python ≥3.10 + wheel | 派生指标口径需自己核对；个别边界（见 4.1）要补 | 低 | **推荐主引擎** |
| L2 语义 | **F. 自建「指标投影层」** | 引擎输出 → ~30 指标 | 选哪些指标、阈值怎么定、token 预算 | 中 | **必做** |
| L3 判据 | G. 规则 + 人工知识库 | 自己维护 YAML | 知识会过期，需版本化 | 中高 | 可行，建议从小场景起步 |
| L3 判据 | H. 击杀邮件统计（zkb/ESI） | ESI killmail / zkillboard | zkb 无官方 API、有速率限制；样本偏差（死掉的配装才被记录） | 中 | 可行，作为「流行度参考」而非真理 |
| L3 判据 | I. 军团 doctrine / 配装站导入 | EVE Workbench、联盟 doctrine 文档 | 抓取合法性与格式不统一 | 中 | 可选 |
| L4 生成 | **J. LLM 提议 + 引擎验证 + 局部搜索精修** | 引擎在环 | 目标函数怎么定义；每轮评估成本 | 中 | **推荐**（唯一务实的组合路线） |
| L4 生成 | K. 纯搜索/退火（无 LLM） | 引擎 | 需要可微/可排序的目标函数，评价维度一多就崩 | 中 | 有条件可行，作 J 的子模块 |
| L4 生成 | L. 训练模型学配装 | 击杀邮件语料 | 数据清洗、GPU、效果不可控、验证成本 | 高 | 不建议（现阶段） |
| L5 接口 | **M. MCP server（Python）** | FastMCP / 官方 SDK | 工具粒度、返回体 token 控制、错误语义 | 低 | **推荐** |
| L5 接口 | N. CLI + Skill | 上下文里的 skill 机制 | 每次都吃命令行输出，交互感弱 | 低 | 可行，作 M 的补充 |
| L6 可选 | O. 价格/成本 | ESI market / Fuzzwork / Adam4EVE | 市场 API 速率与时效 | 低 | 可选加分项 |

## 4. 可行性判断记录（每条写清卡在哪）

### 4.1 明确要自己写的工位（4 个）

1. **应用层命中率**：引擎给了「炮台转速/最佳+失准距离」「导弹爆炸半径/爆炸速度/飞行时间」和「自身信号半径/速度」，但**没有**「对某个具体目标的有效 DPS / 有效 EHP」。
   - 这块要自己按公式合成（目标信号半径、速度、横向角速度、距离）。
   - 卡点：**这是唯一容易和游戏实际不一致的地方**。缓解：公式照抄 pyfa 实现，用 pyfa 做回归测试。
2. **指标投影层**：把每件装备的几十个属性压成「agent 读得懂的一屏」。
   - 卡点：token 预算。原样输出必爆；要设计「概览 → 追问 → 细项」的分级返回。
3. **判据/评分层**：把「好不好」编码成可计算的分数或可读的判词。
   - 卡点：这是**领域知识**，不是技术问题；必须锁定场景才有意义（PvP 单浪 vs 采掘 vs 舰队，判据完全冲突）。
4. **生成/修改的搜索层**：候选生成、剪枝、评估、精修。
   - 卡点：组合空间；必须有剪枝（按技能可用的模块集合、槽位/CPU/PG/标定预算、用途白名单）。好在 `validate` 免费给了合法性护栏，搜索可以放心地「生成—过滤」。

### 4.2 好消息（不用自己解决）

- 堆叠惩罚、热过载、突变模块、模式、指挥脉冲、虫洞 beacon：引擎已实现。
- 合法性校验：引擎已实现（资源/槽位/技能/弹药组/尺寸）。
- 格式解析与输出：EFT / DNA / ESI 配装 / 击杀邮件，全有现成函数。
- 数据新鲜度：上游每日重建，跟版本号即可。
- 并行：释放 GIL，批量评估可以直接多线程。

### 4.3 风险清单

| 风险 | 等级 | 缓解 |
|---|---|---|
| 应用命中率自研部分算错 | 高 | 以 pyfa 结果为基准做对拍；关键结论标注「理论值」 |
| 上游引擎口径与主人预期不同（如 EHP 默认伤害分布 25/25/25/25） | 中 | 明确参数可传，输出时标注假设 |
| 判据主观、场景混淆 | 高 | 先锁一个场景做穿，再谈通用 |
| ESI 接口变更 | 中 | ESI 只做可选增强；核心不依赖 |
| 引擎项目较新（Beta），可能缺边界功能 | 中 | 关键路径做冒烟；异常时降级到 pyfa 裁判 |
| 许可证 | 低 | 引擎 MIT；SDE 数据属 CCP 受其许可；pyfa GPL 仅作本地对拍 |

## 8. 第 2 轮：主人的决定与设计后果

### 8.1 决定（已确认）

| 项 | 决定 |
|---|---|
| Q1 场景 | **先做通用评估，不锁场景** |
| Q2 账号数据 | **不要，纯静态模拟**（无 OAuth、无机库、无技能同步） |
| Q3 生成输入 | **只要自然语言一句话** |
| Q4 交付形态 | **MCP 工具套件** |

### 8.2 由此产生的结构变化

**变化一：判据层重构（原第 4.1 节第③项）**

不再做「场景知识库」，改为两层：

- **通用客观检查**（与场景无关，可判真伪）：合法性违规、资源浪费（CPU/PG/标定大量富余而槽位空置）、模块自相矛盾（双推进器、抗性与装甲类型冲突）、无人机带宽/容量不匹配、弹药与武器不匹配、槽位空转；
- **意图触发检查**（由调用方给出的意图激活）：说到「打深渊」才查电容与抗性分布，说到「打捞」才查牵引与残骸。

**通用评估能给的三类结论**（必须在文档里写死，避免以后自我欺骗）：

1. 客观指标值；
2. 结构缺陷诊断；
3. 相对比较（A 对 B 的 delta）。

**给不了的**：绝对的好坏结论。这是「不锁场景」的直接代价，且不可绕过。**结论权留给调用方 agent**——这其实是对的：工具负责事实与诊断，判断交给会话里的 agent，主人本来也是这么用 agent 的。

**变化二：「自然语言一句话」的层级归属（待定 F1）**

这是本轮最大的分叉，必须拍板：

- **方案 α（MCP 内嵌 LLM）**：一句话直达工具，MCP 内部再解析意图并生成。
  - 好处：调用侧零负担。
  - 代价：需自备模型与 key、双模型串联、不可复现、失败归因困难、成本随调用线性涨。
- **方案 β（MCP 只做确定性原语）**：NL 由调用方 agent 解析成结构化参数，MCP 只做「给定参数 → 给结果」。
  - 好处：与「给 agent 用」天然一致；可复现；可单测；成本低；失败点单一。
  - 代价：调用方 agent 要负责意图抽取与追问（但它本来就在做这件事）。

**女仆建议 β。** 理由：主人的原始需求第一句是「给 agent 用」，而 agent 的核心能力恰好就是自然语言理解；把 NL 理解塞进 MCP 等于在工具里再养一个 agent，收益重叠、成本翻倍。

**变化三：无账号数据，口径必须显式定义（待定 F2）**

没有机库和技能，会漏掉两个关键前提，必须显式规定，否则结果无意义：

- **技能档位**：默认全技能 L5？还是 T2 所需最低技能？还是按船型给「典型 Omega 号」？
- **候选池**：生成时可选模块集合。若不限制，等于「全宇宙全部可装模块」，组合爆炸且不现实（死亡空间装备、势力装备、突变模块）。
  - 建议分档：**A 档 全技能 + T2 上限**（体现船只上限，默认）；**B 档 T1 基线**（新手/低成本）；**C 档 预算受限**（需接入价格，后置）。

### 8.3 顺带发现：`sources` 归因能力

引擎的 `sources: true` 会为每个属性返回**全部修改来源**：来自哪件装备/技能/效果、什么算子、堆叠惩罚系数、是否因状态不足而未生效。

这是把「数值」变成「解释」的**唯一现成入口**，价值极高：能回答「为什么 DPS 只有 240」「为什么电容在 40% 稳定」「换了这发弹药涨了 18% 是哪里来的」。

→ 结论：工具面里必须有一个 `explain` 类能力，这是本套件区别于「查表工具」的核心。

### 8.4 工具面初拟（第 3 轮细化，非定稿）

| 能力 | 作用 | 关键设计点 |
|---|---|---|
| `eval` | 配装 → 指标卡 + 违规 + 结构诊断 | 返回分级（概览/追问再取细项）控 token |
| `compare` | 两套及以上配装 → delta 表 | 同船型优先；不同船型只比同类指标 |
| `explain` | 某指标 → 归因链（用 `sources`） | 需要限深，否则归因链爆炸 |
| `generate` | 需求 → 多方向候选 + 假设清单 | 不给「唯一最优」；每个候选必须带 assumptions |
| `patch` | 现有配装 + 缺陷/目标 → 修改方案集 + 前后 delta | 复用 `validate` 做护栏 |
| `parse` | EFT / DNA / ESI / 击杀邮件 → 统一结构 | 引擎已实现，只做壳 |
| `search` | 类型检索与属性查询 | 需本地类型索引（SDE 已含名称） |

### 8.5 新的卡点

- **无场景下 `generate` 的目标函数**：多目标（火力/生存/机动/成本）且权重未知 → 只能给「多方向候选」，每个方向自带取舍说明。这是设计要求，不是缺陷。
- **返回体 token 预算**：MCP 返回 JSON 会进 agent 上下文，指标卡字段必须精简。
- **未做 benchmark**：单套计算耗时未知，决定 `generate` 一次能评估多少候选。

### 8.6 第 3 轮议程

1. 拍 F1（NL 归属）与 F2（技能档位 / 候选池）。
2. 定**指标卡第一批字段**（投影层落地）。
3. 定 `generate` 的候选生成流程与「假设清单」契约。
4. 定工具清单与命名。

## 9. 第 3 轮：目标升级为「战况理解系统」

### 9.1 主人的新表述（已确认）

不局限于单一工具，可以是 **MCP / RAG / 管道 / 数据库** 等组合。能力阶梯扩到五层：

> 读取配装 → 生成配装 → 理解配装 → 理解配装在**战报（BR）**里的意义 → 根据 BR 与配装**理解一场战争**

这条线一拉长，「配装工具」就变成了「战况理解系统」，架构必须分层，不能是 MCP 单体。

### 9.2 能力阶梯与可行性

| 层 | 能力 | 可行性 | 关键依赖 | 卡点 |
|---|---|---|---|---|
| L1 读取 | EFT / DNA / ESI / killmail → 统一结构 | **高** | 引擎自带 loader | 无 |
| L2 生成 | 需求 → 候选配装 | **中高** | 引擎 + 剪枝 | 多目标权重未定 |
| L3 理解 | 指标 + 归因解释 | **高** | 引擎 `sources` | token 预算、判据主观 |
| L4 战报语境 | 这套配装在这场战斗里扮演什么角色 | **中高** | killmail 语料 + 配装反算 | 攻击者配装不可知；战斗边界定义 |
| L5 战争理解 | 一场战争的战况画像 | **量化部分高 / 战略部分不可行** | 语料库 + 时间序列 | 意图与胜负不在数据里 |

### 9.3 BR 数据可得性（2026-10-18 实查）

**zKillboard API 现状良好，且足以自建战报**（[API 文档](https://zkillboard.com/api/docs/)）：

- 读接口**无需鉴权**；返回 **ESI 格式 killmail + zkb 元数据**（hash、总价值、points、solo/awox、labels）；
- 过滤维度：角色/公司/联盟/势力/船型/物品组/**星系/星座/区域**/标签/安全等级/时间窗/最低价值/页码；
- 单页 200 条 × 页码 1–100 = **单次查询上限 2 万条**；小于 5 分钟的 killmail 不下发；
- 要求：描述性 `User-Agent`、`Accept-Encoding: gzip`、**本地缓存 + 请求间隔**（1 小时客户端缓存）；
- 另有 `/api/prices/date/{date}/`：**按日的历史物价表**（2003 至今）→ 战报的 ISK 估值可以按当日价格重算，而不是用今天的价格穿越回去；
- 站内还有 Campaigns（结构攻防事件）与 Sovereignty 页面 → 战争层的结构性事件补充。

**推理**：一场战斗 = 某个星系 + 时间窗 + 参与者图 → 用 zkb 查询就能把 killmail 集合拉全。**不需要依赖第三方战报站**。

**已排除的路径**：

- RedisQ（旧实时订阅通道）——`redisq.zkillboard.com` 已 DNS 不解析，**已死**；实时只能走 zkb WebSocket。
- 第三方 BR 站（warbeacon.net 等）为 JS 单页应用，**未找到公开 API**，HTML 抓取脆弱且易失效 → 不作为依赖。

### 9.4 关键的不对称（决定 L4 的能力上限）

这是本轮最重要的发现，必须写死：

| 角色 | 数据 | 可评估性 |
|---|---|---|
| **受害者** | 完整配装（含槽位 flag、数量、部分弹药） | **可完整评估**（引擎 `load_killmail` 直接转配装） |
| **攻击者** | 仅 `ship_type_id` / `weapon_type_id` / `damage_done` / `final_blow` / 归属 | **配装不可知** |

→ 结论：战报分析只能是「**从受害者的损失反推战局**」，不能是「评估双方配装」。攻击方只有船型、武器类型与伤害占比。

### 9.5 可算 / 半可算 / 不可算（划清边界，防止幻觉）

**可算（必须由代码算）**：
船型与吨位结构；ISK 交换比（按当日价格）；**攻击方伤害类型 vs 受害者抗性缺口命中率**；后勤/电子战舰存在与比例；时间线（崩溃过程、增援到达）；空间分布与聚类；same-site 反复交战；doctrine 演化（按船型+武器组合聚类）；损失率与存活率。

其中「伤害类型 vs 抗性缺口」是本系统最有价值的确定性产出：受害者配装可算抗性分布，攻击方武器与弹药可推伤害类型，killmail 自带 `damage_done` —— 三者一碰，就能算出「这套死在什么地方」。

**半可算（需规则+假设）**：
单封 killmail 的角色判定（侦察/主战/后勤/电子战）——按船型与槽位规则可判大部分，边界模糊处要标注置信度。

**不可算（数据里根本不存在）**：
指挥意图与决策、语音沟通、未发生的事（对方没来/跑了）、精确的 DPS 时间曲线（`damage_done` 是累计值）、攻击者配装、战争胜负与政治背景。

→ 第 L5 层若要说「为什么打」，只能引入外部语料（官方 patch/dev blog、联盟 doctrine 文档、战史长文、社媒舆论）做 RAG，且结论必须标注为「当时的说法」，不是事实。

### 9.6 架构结论：不是单一 MCP，是六件东西

| # | 组件 | 职责 | 形态 |
|---|---|---|---|
| 1 | 同步管道 | SDE 每日比对 build number；killmail 增量拉取与去重 | 定时脚本 |
| 2 | 事实库 | killmail、派生配装、估值、地点、聚合表 | **DuckDB / SQLite + parquet**（百万行级列式聚合） |
| 3 | 计算引擎 | 配装计算、校验、格式互转、归因 | `eveshipfit-dogma-engine` 包壳 |
| 4 | 分析层 | BR 聚类、战况聚合、抗性对位、doctrine 识别 | **确定性算法，非 LLM** |
| 5 | 语境层 | patch / doctrine / 战术术语 / 战史 | RAG（可选，最后做） |
| 6 | 接口层 | 只暴露查询/计算/分析原语 | MCP + agent 编排 |

**核心矛盾与解法**：agent 现场提问不能等计算。

- 单场战斗：数百~数千 killmail，逐封算配装（引擎毫秒级）→ 秒级可接受，可现场算；
- 一场战争：10 万+ killmail → **必须离线预计算**（只算受害者、可采样），agent 只查聚合表。

→ 结论：**离线预计算与在线查询必须分离**。这是架构上不能妥协的一条。

### 9.7 三条硬原则

1. **确定性优先**：数值与统计只由代码算，LLM 只做选择、解释与叙事。任何让 LLM 直接「读 killmail 说结论」的设计都会变成幻觉生成器。
2. **战斗边界显式化**：什么算「一场战斗」必须显式定义（时间窗 / 空间范围 / 参与者图连通性），并允许切换。不同定义会给出不同结论，隐藏定义等于制造争议。
3. **结论可溯源**：每条结论都要能指回「哪封 killmail、哪个属性、哪个假设」。

### 9.8 第 4 轮议程

1. 战报层先做**单场**还是直接上**多场/战区**？（建议先单场穿通，再聚合）
2. 事实库选 DuckDB 还是 SQLite？（建议 DuckDB 做分析、SQLite 做便携）
3. RAG 语料优先级：官方 patch / 联盟 doctrine / 战术术语 / 战史长文，先做哪个？
4. 是否需要实时？（实时 vs 事后补全，成本差异大）
5. 第 2 轮遗留的 F1（NL 归属）与 F2（技能档位 / 候选池）尚未拍板。

## 10. 第 4 轮：范围收敛到 L1–L3（读取 / 生成 / 理解）

### 10.1 范围决定

主人明确：**暂不考虑战报与战争层**。当前目标只有三件：**读取配装、生成配装、理解配装**。

- 第 9 节整体**挂起**，作为后续扩展保留，不作为本期设计依据；
- 但第 9 节的结论仍有效并影响本期：①确定性优先；②所有输出必须带 assumptions；③离线计算与在线查询分离（大船生成时同样适用，见 10.3）。

### 10.2 L1 读取：输入形态与真实坑

**输入形态矩阵**：

| 形态 | 来源 | 可行性 | 备注 |
|---|---|---|---|
| EFT 文本 | 游戏内剪贴板，最常见 | 高 | 引擎支持；英文名，或多语言名（需 `names.dat`） |
| DNA 链接 | 聊天/论坛分享 | 高 | 引擎支持 |
| 结构化 JSON | agent 自己构造 | 高 | 天然最优，作为内部主格式 |
| 自然语言描述 | 「我开乌鸦，四个巡航导弹」 | 中 | **由调用方 agent 转成结构化**，工具不做 NL |
| ESI 已存配装 | 账号数据 | — | **已排除**（第 2 轮决定：不做账号数据） |

**已知会踩的坑（都是真实现象，不是假设）**：

1. **同名多版本**：同一名字可能对应不同 meta 等级/势力变体，匹配错误会静默算错。→ 解析失败必须报错而不是「猜一个」。
2. **空槽与状态**：`[Empty High slot]`、`Offline` 标记、`x1` 后缀、弹药行依附上一行 → 行级语义，不能简单字符串切分。
3. **位置归属**：无人机放 drone bay 还是货舱、rig 尺寸是否匹配船体 → 引擎能校验，但要在结果里显式呈现。
4. **突变模块（深渊）与势力装备**：属性不是静态的，必须走 `mutation` 字段；纯名字无法表达。

**设计要点（关键，容易被忽略）**：

> **解析失败必须是「可修复的错误」，不能是布尔值。**

agent 的核心能力是自修。如果工具只返回 `invalid`，agent 无法闭环；必须返回：第几行、原始文本、匹配失败的词、**最接近的候选类型名**、以及是哪类问题（船名/模块名/数量/槽位）。

另一个决定：**内部一律用 `type_id`，名字只是入口**。所有跨层数据（指标卡、生成结果、对比）都以 type_id 为键，避免名字漂移。

### 10.3 L2 生成：四条技术路线与唯一可行的那条

| 路线 | 做法 | 可行性 | 判断 |
|---|---|---|---|
| R1 模板填充 | 维护 doctrine 模板，换抗性/弹药/rig | 高 | 好做但覆盖窄，模板库要人工养 |
| R2 联合搜索（CSP/退火） | 全槽位同时搜索 | 低 | **组合爆炸**，实测不可行 |
| R3 LLM 提议 + 引擎验证 + 局部精修 | LLM 出骨架 → 引擎打分 → 搜索微调 | 高 | **推荐**（唯一务实） |
| R4 纯穷举 | 遍历所有组合 | 不可行 | 数量级不允许 |

**为什么 R2 不可行（量化）**：战列舰约 8 高 / 6 中 / 5 低 / 3 rig，仅高槽可选武器就几十种，低槽模块上百种 → 组合数量级轻松到 $10^{10}$ 以上。即便引擎单次计算 1ms，也跑不完。

**唯一可行的搜索结构：分阶段，不是联合搜索**

1. 定角色（PvE 清怪 / PvP 单浪 / 后勤 / 电子战）；
2. 定武器系统（决定高槽、弹药、伤害类型、射程逻辑）；
3. 定防御体系（中/低槽的盾甲结构选择 + 抗性方向）；
4. 定 rig 与辅助（电容、机动、应用）；
5. 引擎打分 → 局部替换精修（单槽位贪心 + 少量交叉）。

每一阶段候选数都被压到几十~几百，总评估量落在**可现场计算**的范围（具体上限待 benchmark）。

**「好」的定义问题（本期最大障碍）**

多目标（火力 / 生存 / 机动 / 电容持续性 / 成本 / 应用）且权重依场景变化。技术解法：

- 不做「单一最优」，输出 **Pareto 前沿上的多个候选**；
- 每个候选标注**取舍说明**（用 B 换掉了 A 的什么）；
- 权重由调用方 agent 从主人那句自然语言里取（「便宜点」→ 成本权重高）。

→ 这也是为什么 NL 层必须由 agent 承担（见 F1）：工具不该猜主人想要什么。

### 10.4 L3 理解：输出契约

「理解」不能只是把数字列出来。四项能力：

| 能力 | 内容 | 技术实现 | 可行性 |
|---|---|---|---|
| 指标卡 | 概览（10–20 项）+ 细项按需取 | 引擎结果 + 投影层 | 高 |
| 结构诊断 | 超载/错槽/自相矛盾/槽位空转/带宽不匹配 | 引擎 `validate` + 规则 | 高 |
| **归因** | 「为什么 DPS 只有 240」 | 引擎 `sources` 逐条来源链 | 高（需限深） |
| **灵敏度** | 「换 T2 弹药：DPS +18%，成本 ×3」 | 变体重复计算 + delta | 高（最有决策价值） |

**必须带 assumptions**，否则 agent 会把假设当事实传播：技能档位、伤害剖面（默认 25/25/25/25）、是否热过载、是否虫洞/ beacon、rig 尺寸、是否含装填。

**返回分级**（token 预算）：

- `overview`：10–20 字段，约 300–500 token；
- `detail`：指定指标或指定装备的细项；
- `explain`：指定指标的归因链，限深（默认 2 层）。

### 10.5 三处最容易翻车

1. **引擎口径未实测**：pass 4 指标的具体定义（EHP 是否含伤害剖面、电容稳定是否满技能、DPS 是否含装填）尚未验证，一旦与预期不一致，所有下游结论都偏。
   → **建议做一次冒烟验证**（装引擎、算一艘船、核对 2–3 个数字），成本极低，收益是「整个项目的数值地基确认」。
2. **EFT 解析的歧义**：同名多版本 + 突变模块，静默错误比报错更危险。
3. **生成的搜索深度**：分阶段搜索能跑，但「精修」到什么程度、评估多少次，取决于单次耗时（未 benchmark）。

### 10.6 待拍板（阻塞设计）

| 编号 | 问题 | 影响 |
|---|---|---|
| F1 | 自然语言解析放 MCP 内（α）还是交给调用方 agent（β） | 决定工具签名与是否要内嵌模型 |
| F2 | 默认技能档位（全 L5 / T2 最低 / 双档） | 决定所有指标数值 |
| F3 | 默认候选池（全 T2 上限 / T1 基线 / 双档） | 决定生成结果的现实性 |
| F4 | 生成只允许「从零生成」还是也允许「在给定配装上改」 | 后者的可行性高一个数量级，且更实用 |
| F5 | 是否接受「多候选 + Pareto」而非「单一最优」 | 决定输出契约 |

### 10.7 下一步（待主人点头）

1. 拍 F1–F5；
2. **冒烟验证**：装引擎 → 算 1 艘船的完整指标 → 核对 pass 4 口径与单次耗时（这是唯一能把「可行」变「已证实」的动作）；
3. 据实测数据定生成搜索的评估预算；
4. 最后才切工具与命名。

## 11. 第 5 轮：范围收敛到 L1 读取 + L3 理解

### 11.1 范围决定

主人明确：**生成也后置**。本期只做两件事：**读取配装**、**理解配装**。

- 第 10.3 节（生成 / 搜索）整体挂起；
- 第 9 节（战报/战争）挂起；
- 保留有效结论：确定性优先、输出带 provenance、离线计算与在线查询分离。
- 判断：这是正确的收敛。生成是理解的下游——**理解做不准，生成只能是噪声放大器**。

### 11.2 读取层：三个契约

读取不是「能解析就行」，要立三个契约，否则下游全不可靠。

**契约一：输入归一化**

所有输入（EFT / DNA / 结构化 JSON）→ 统一内部结构，键一律 `type_id`。名字只作为入口，绝不进下游。

**契约二：错误必须可修复**

解析失败返回结构化错误，不是布尔值：

```
{ line: 3, raw: "200mm AutoCannon", failed_at: "module_name",
  candidates: ["200mm AutoCannon I", "200mm AutoCannon II"], reason: "ambiguous" }
```

理由：agent 的自修能力完全依赖这个反馈。**省掉的结构化，就是后续每一次失败的循环成本。**

**契约三（本轮新增，最重要）：值来源三态**

任何输出的每个值，必须能回答「这个数是哪来的」。三态：

| 态 | 含义 | 例 |
|---|---|---|
| `measured` | 由输入直接决定 | 船型、模块、槽位、数量 |
| `assumed` | 输入缺失，用了默认值（必须显式给出） | 技能全 L5、状态 active、伤害剖面 25/25/25/25、满装填 |
| `unknown` | 无法推断，且不应用默认值代替 | 突变模块的具体属性、货舱内容、弹药是否真的带够 |

**为什么要三态而不是直接填默认值**：主人贴的 EFT 里根本没有技能信息。静默填 L5 会让 agent 把一个「满技能理想值」当成「这套配装的实际表现」传播出去。`assumed` 与 `unknown` 分开，等于把「不可知」从「假设」里救出来。

### 11.3 理解层：五项产出

| # | 产出 | 内容 | 实现 |
|---|---|---|---|
| 1 | 指标卡 | 概览/细项分级 | 引擎 pass 4 + 投影层 |
| 2 | 结构诊断 | 违规、自相矛盾、槽位空转、带宽不匹配 | `validate` + 规则 |
| 3 | 归因 | 「为什么 DPS 只有 240」 | `sources` 来源链，限深 |
| 4 | 灵敏度 | 「换 T2 弹药：DPS +18%、成本 ×3」 | 变体重算 + delta |
| 5 | **能力画像** | 这套能干什么、干不了什么 | 规则推理（见 11.4） |

前四项是「事实层 + 数值层」，第五项才是「理解」的真正形态。

### 11.4 能力画像（capability envelope）——本轮核心设计

**问题**：agent 不需要理解 200 个属性，它需要知道「这套能不能干某事」。把数字翻译成边界，才是理解。

**输出形态**（判词 + 依据，不是分数）：

```
续航：电容在 32% 稳定（无外部干扰时持续输出可行）
输出：持续 318 DPS @ ≤15km，有效射程带 4–18km；超出 18km 打不动
生存：EHP 42k，抗性缺口在动能（−12% 相对最优抗性）
脱离：最大速度 1.8km/s，alignTime 5.2s —— 被点被抓时无法脱离
缺陷：无反跳、无反扰 → 抓不住人，也不具备脱离对抗能力
```

**技术实现**：从指标做规则推理，规则表与外置配置（YAML），每条规则带：

- 触发条件（阈值比较）；
- 判词模板；
- **confidence**（`hard` = 纯数值可比；`heuristic` = 依赖经验阈值）。

**可行性**：高。纯数值比较，无 LLM 参与，可单测、可解释。

**风险**：阈值表是领域经验，会过时、会主观。→ 因此**阈值外置 + 标注 confidence + 允许覆盖**，不做成硬编码真理。

### 11.5 抗性对位：一个小而高价值的切入点

「理解」里最硬的一块，是把两个独立维度合成一个结论：

- 自身：抗性分布（可算）
- 对手：伤害类型分布（**这是知识**——某族 NPC / 某类弹药的伤害构成是稳定事实）

→ 得到「有效 EHP」与「最怕什么伤害」。例：说「打天使怪」→ 爆炸/动能为主 → 换成对应抗性剖面重算 EHP → 指出缺口。

这条路的好处：只需要一张**敌人伤害剖面表**（NPC 族系 + 弹药类型），规模小、稳定、可人工校对，是 RAG/知识库最小可行的落脚点。且完全不需要生成能力就能交付价值。

### 11.6 指标卡字段草案（overview，约 25 项）

- 船：名称 / type_id / 级别
- 防御：EHP 总量 + 盾/甲/构分项；四系抗性（实际值）；按剖面加权后的有效 EHP
- 火力：武器系统；DPS（含/不含装填）；齐射；Alpha；伤害类型构成
- 应用：最佳射程 / 失准（或爆炸半径 / 爆炸速度 / 飞行时间）；转速
- 无人机 / 战斗机：DPS、带宽与容量占用
- 电容：稳定百分比 或 耗尽时间；峰值消耗
- 机动：最大速度 / alignTime / 质量 / 信号半径
- 电子：锁定距离 / 扫描分辨率 / 最大锁定数
- 资源：CPU / PG / 标定 使用率
- 校验：violations
- provenance：技能档位 / 状态 / 伤害剖面 / 装填 的三态标记

预估 300–600 token/套，可接受。

### 11.7 风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| pass 4 口径未实测 | **高** | 冒烟验证（见 11.9） |
| 阈值表主观/过时 | 中 | 外置配置 + confidence 标注 + 可覆盖 |
| EFT 歧义导致静默算错 | 中 | 歧义一律报错，不猜 |
| 指标卡字段选错（选了没用的、漏了关键的） | 中 | 先用草案跑几套真实配装，看哪些字段真被 agent 用到 |

### 11.8 默认决定（主人未反对即按此推进）

1. 自然语言解析交给调用方 agent（工具只吃结构化参数）；

## 12. 第 6 轮：冒烟测试结果（实测，非推测）

### 12.1 测试条件

- 引擎：`eveshipfit-dogma-engine` 13.6.0 + `eveshipfit-sde`（SDE build **3607705**），Python 3.13 隔离环境
- 样本：killmail **139246907**（2026-10-18T05:23:03Z，system 30000267），受害者 **Hecate**，31 件（含货舱），2 名攻击者（同为 47270）
- 测试脚本：`.tmp_eve_smoke/smoke.py` / `smoke2.py` / `smoke3.py`

### 12.2 通过的项

| 项 | 结果 |
|---|---|
| `load_killmail` | ✅ 直接产出完整可读 EFT（含货舱分类正确） |
| SDE 加载 | ✅ 一次加载，进程内复用 |
| **EFT 往返无损** | ✅ `save_eft → load_eft → calculate`，EHP/DPS/alpha/alignTime/cpu/pg 全部完全一致 |
| **alpha 聚合规则** | ✅ `ship alpha = Σ 逐装备 volley`，实测比值 **1.0000** |
| **堆叠惩罚** | ✅ 2× Magnetic Field Stabilizer II → 伤害 ×1.1956 ≈ 1.1 × 1.1^0.87，符合 EVE 规则 |
| **EHP 定义** | ✅ `EHP = 盾EHP + 甲EHP + 构EHP`，等式严格成立 |
| 计算耗时 | ✅ **0.30–0.33 ms/次**（含 validate 0.38 ms）→ 单线程约 **3000 次/秒** |

> 顺带结论：**算力不是瓶颈**。早前担心生成阶段 $10^{10}$ 组合算不完，按 3000 次/秒，算力可以覆盖几十亿次评估。真正的瓶颈是候选生成质量与剪枝，不是 CPU。（生成已后置，此处仅记录）

### 12.3 发现的口径陷阱（四个，都会静默算错）

**陷阱一：属性单位不统一**

- `alignTime = 11.60`（秒）
- `cycleTime = 2177.68`（**毫秒**）；实测 `volley / dps = 2.1777 = cycleTime/1000`
- 抗性类属性是「无量纲份额」，部分属性是百分比

→ 投影层必须自带**单位表**，否则 agent 会输出「射速 2177 秒」这种结论。

**陷阱二：per-type 抗性属性不是抗性，是「按伤害剖面加权后的份额」**

实测（剖面 25/25/25/25 vs 纯 EM）：

| 属性 | 25/25/25/25 | 纯 EM |
|---|---|---|
| `shieldEmReso` | 0.21875 | **0.875** |
| `shieldExpReso` | 0.109375 | **0** |
| `armorEffReso` | 0.470156 | 0.425 |

且严格满足 `Σ per-type = effectiveResonance`（护甲 0.470156 = 0.470156）。

→ 真实共振率 `r_i = per-type_i ÷ w_i`，25/25/25/25 时即 **×4**。**直接当抗性百分比读，会差 4 倍。**

**陷阱三：`volley` 只在装备级，ship 级没有**

ship 聚合属性里 `-21 damageVolley` **不存在**（返回 `None`）。必须自己按装备求和。反之 `alpha/dps/EHP` 在 ship 级有。

**陷阱四：状态（state）是引擎猜的，而它决定生死**

killmail 里**没有任何状态信息**。引擎按「导入配装」的默认规则补了 `active` / `overload`。实测把状态全部改成 `online`：

| 指标 | 引擎补的 active | 全 online |
|---|---|---|
| DPS | 358.2 | **0.0** |
| 电容稳定 | 0% | 100% |
| 峰值耗电 | 23.23 | 0 |
| alignTime | 11.60 | 7.86 |
| velocityBoost | 488.7 | 0 |

→ **同一份配装，"能不能打"取决于一个没人提供的字段**。这是第 11.2 节三态设计的最强证据：`state` 必须归入 `assumed`，且必须显式暴露。

### 12.4 技能缺失导致的误判（量化）

无 `character` 时（引擎默认：**没有技能加成**，不是满技能）：

| 技能档位 | 违规数 | EHP | DPS | cpuFree | powerFree |
|---|---|---|---|---|---|
| 无技能 | **70**（68 技能 + 2 资源） | 7585 | 226 | −75 | −18 |
| 按最低要求补齐（19 个技能） | 2 | 8126 | 300 | −22.5 | −18 |
| 该技能组全 5 | 1 | **9172** | **358** | +5 | **−4.5** |

**结论**：
1. 无技能时 `validate` 会吐出 **68 条假违规**，几乎全是幻觉——**不带技能做合法性判断等于没用**。
2. 技能档位使 EHP 波动 **+21%**、DPS 波动 **+58%**。默认技能档位不是一个「随便选」的参数。
3. 即使全技能 5，**PG 仍超 4.5**（−4.5）。这艘实死船只可能带了**植入体**（killmail 不含）。→ **killmail 还原的配装未必合法**，合法性判词必须标注「依据还原配装，未含植入体」。

### 12.5 字段可信度分级（决定哪些能进判词）

| 等级 | 字段 | 依据 |
|---|---|---|
| **A 可信**（实测等式成立） | `EHP`、`shieldEhp`/`armorEhp`/`hullEhp`、`damageAlpha`、`dpsWithoutReload`/`dpsWithReload`、`alignTime`、`cpuFree`/`powerFree`/`upgradeFree`、`capacitorDepletesIn`/`capacitorStablePercentage`、`velocityBoost` | 等式与聚合规则均实测通过 |
| **B 需换算** | per-type 抗性（÷权重）、`cycleTime`（毫秒）、`velocityBoost`（百分比，单位待确认） | 陷阱一/二 |
| **C 不可用** | `maxTargets`（恒为 0，全技能档也为 0）、ship 级 `volley` | 实测缺失 |
| **D 需对拍** | ~~抗性绝对值~~ → **已于第 7 轮确认正确，升为 A 级**（见 14.2） | ESI 官方基础值 12/12 项一致，DC II 加成倍数完全吻合 |
| **E 依赖假设** | 一切与 `state` 相关的（DPS、电容、alignTime、速度） | 陷阱四 |

### 12.6 对设计的三条修正

1. **能力画像的阈值必须建立在 A 级字段上**；D 级字段（抗性）在未对拍前只能给相对结论（「这套偏好动能抗」），不能给绝对百分比判词。
2. **`assumed` 必须覆盖 `state`**，且默认值要显式可覆盖；对 killmail 来源的配装，应在输出里直接标「状态由导入规则推定」。
3. **合法性判断必须与技能假设绑定**：没有技能时不要输出 `violations`，只输出 `skill_requirements`（缺什么技能）——这本身就是有价值的信息，且不会误导。

## 13. 第 7 轮：职责划分 —— 代码 / 知识库 / skill 的边界

### 13.1 主人的判断

「感觉都是可以用 skill 或 RAG 等知识库限制和解决的问题。」

**部分成立**：确实有一大块是知识问题，而且这类项目没有知识库会寸步难行。
**但必须分三类**：把确定性约束交给概率模型（LLM + 检索），是本项目最容易埋下的系统性错误。

### 13.2 判据（一句话决定归宿）

> **「错了会不会静默出错？」**

- 会静默出错（算错了但看起来正常）→ **必须进代码**，且必须单测；
- 错了有可见症状（术语说错、判据过时，用户能看出来）→ 可以进知识库；
- 只影响表述方式（怎么措辞、先查什么）→ **skill**。

### 13.3 实测问题的逐项分派

| 问题 | 归宿 | 理由 |
|---|---|---|
| 单位不统一（`cycleTime` 毫秒 vs `alignTime` 秒） | **代码** | 静默错；投影层直接输出统一单位 |
| per-type 抗性 = 权重 × 共振率 | **代码** | 静默错 4 倍；输出时已换算成真抗性 |
| `volley` 只在装备级 | **代码** | 聚合是确定性操作 |
| `state` 由导入规则推定 | **代码**（provenance 标记） | 标记是机械操作 |
| └ 但「真实状态是什么」 | **无解** | 数据里根本没有，知识库也补不出来 |
| 技能档位缺失 | **代码**（默认值协议）+ **知识库**（典型档位） | 协议是确定性的；「典型档」是知识 |
| 植入体缺失（killmail 不含） | **无解，只能标注** | 数据缺口 |
| 抗性绝对值是否准确 | **对拍（pyfa）** | 这是基准数据问题，**检索不能替代计算** |
| 敌人伤害剖面（NPC 族系 × 四系） | **知识库** | 真知识，稳定、可校对 |
| 弹药伤害构成 | **代码（不是知识库）** | SDE 里就有 `emDamage`/`explosiveDamage`/`kineticDamage`/`thermalDamage`，直接算 |
| 异常/远征难度门槛 | **知识库**（需标 confidence） | 经验值，主观 |
| 术语与 doctrine 语义 | **知识库** | 真知识，但会过时 |
| 调用规程、表述纪律 | **skill** | 只管流程与措辞 |

### 13.4 为什么「把换算推给 RAG」是反模式

如果设计要求「agent 记得 cycleTime 是毫秒」「agent 记得抗性要除以权重」：

1. **不可测**：没有任何单测能证明 LLM 每次都记得；
2. **不可复现**：换个模型、换个上下文长度，行为就变；
3. **成本随调用线性增长**：每次都检索一遍；
4. **失败静默**：检索没命中或幻觉时，输出照样「看起来合理」；
5. **责任错位**：把「绝不能错」的部分，交给了最不可控的一环。

正确做法是反过来的：**让返回结构自解释**——字段名带单位（`cycle_time_ms` → 改成 `cycle_time_s`）、带 provenance、带语义注释。这比写 skill 便宜，而且可单测。

### 13.5 RAG 真正的用武之地（共同特征：稳定、可校对、规模小、错了看得见）

1. **敌人伤害剖面表**：NPC 族系（天使 / 萨沙 / 天蛇 / 血袭者 / 古斯塔斯 / 无人机 / 三神裔……）× EM/EX/KI/TH；
2. **异常与远征的难度门槛**：需要多少 EHP、多少 DPS 才够（经验值，必须标 confidence）；
3. **术语与 doctrine 语义**：「坦克」「风筝」「阵地战」「超载」在具体语境下的含义；
4. **典型技能档位**：新手 / 标准 / 满技能三档的定义。

→ 这四件事恰好也是**唯一值得现在做 RAG 的位置**。注意：弹药伤害构成**不在**此列（SDE 已有）。

### 13.6 skill 的正确定位

skill 不是「限制工具」，是「**规程 + 表述纪律**」：

- 什么时候该调用哪个能力；
- 字段语义与 provenance 怎么处理；
- `assumed` 时怎么表述（**不许把理论值说成实际表现**）；
- 禁止事项（不许拿 DPS 当击杀时间；不许在 D 级字段上给绝对判词）。

skill 管不住「agent 读错字段」——**那只有结构化字段名和代码能管住**。

### 13.7 结论

> 工具的正确形态：**让数据不需要解释就能用**。
> 代码负责「绝不能错的部分」，知识库负责「EVE 的常识」，skill 负责「怎么用这套工具」。

三者比例大约 = 代码 70% / 知识库 20% / skill 10%，且**代码那 70% 决定了另外 30% 有没有意义**。

### 14.2 抗性验证：完整闭环（实测）

验证路径：**ESI 官方数据** ↔ **引擎裸船** ↔ **引擎加装 DC II** ↔ **官方模块属性**。

**第一步：引擎裸船 vs ESI 官方（type 35683 Hecate）**

| 层 | EM | EXP | KIN | THM |
|---|---|---|---|---|
| 护甲（官方 / 引擎） | 0.5 / 0.5 | 0.9 / 0.9 | 0.325 / 0.325 | 0.4875 / 0.4875 |
| 结构（官方 / 引擎） | 0.67 / 0.67 | 0.67 / 0.67 | 0.67 / 0.67 | 0.67 / 0.67 |
| 护盾（官方 / 引擎） | 1.0 / 1.0 | 0.5 / 0.5 | 0.3 / 0.3 | 0.6 / 0.6 |

**12/12 项完全一致。**

**第二步：DC II 的实际加成（引擎实测倍数 vs 官方模块属性）**

| 层 | 引擎实测倍数 | Damage Control II 官方属性 | 一致 |
|---|---|---|---|
| 护甲 | ×0.850 | `armor*DamageResonance = 0.85` | ✅ |
| 护盾 | ×0.875 | `shield*DamageResonance = 0.875` | ✅ |
| 结构 | ×0.600 | `hull*DamageResonance = 0.60` | ✅ |

**第三步：叠加方式**——`最终共振率 = 基础共振率 × 模块共振率`，三层全部严格成立（层内四系倍数完全相同）。

**结论**：
1. 抗性算法**正确**，此前「结构抗性 59.8% 与常识不符」是**我拿 T1 护卫舰的直觉套 T3 驱逐舰**，不是引擎的问题。
2. 抗性体系**全部原料都在 SDE 里**——模块自带共振率属性，无需任何硬编码知识，也**不需要知识库**。
3. 因此 `sources` 的输出也验证了陷阱二：值 = 伤害剖面权重（`pre_assign 0.25`）× 真实共振率（`post_mul 0.525`）。

→ **抗性从 D 级升为 A 级，可直接进多视角结论。**

### 14.3 设计变更一：从「判据」改为「多视角」

原「能力画像 + 阈值判词」的设计**降级**：不再产出「这套好不好」的结论，改为从若干独立视角各给一份观察。每份只含**事实、边界、可疑点**，不做汇总评分、不做排名。

| 视角 | 看什么 |
|---|---|
| 火力 | 输出量、射程带、伤害类型构成、装填占位 |
| 生存 | EHP 分项、四系抗性几何（哪边最薄）、修复能力 |
| 机动 | 速度、alignTime、信号半径（三者都是"被抓"的变量） |
| 资源 | CPU/PG/标定余量、无人机带宽与容量、无人可用槽位 |
| 约束 | 技能要求、非法项、需植入体才能成立的项 |
| 不稳定 | 电容是否可持续、是否依赖外部支援（遥修/传电） |

**好处**：避免把"阈值判词"做成伪权威；也正好对上 agent 需要多重理解的用法。

### 14.4 设计变更二：技能档约定

**默认档 = 全部技能 4 级 + 每个模块的最低要求取 max(4, required)。**

理由（主人给出）：游戏里大多数玩家会把技能挂到 4 级，那是最经济的点；T2 装备要求 5 级的，按最低要求补到 5。

实现注意（本轮新增的一条约束）：

> 合法性判断的措辞必须改。在给定技能档下装不下时，输出「**该档位下超载：PG 缺 12.4**」，而不是「配装非法」。因为换一档技能或加植入体就可能合法。

### 14.5 设计变更三：`state` 从「标注」升级为「情景枚举」

主人指出：战斗中装备状态随时变化，而这正是 agent 给出多重理解的价值所在——「一场数据上不会输的战斗却产生了 kb，从 state 的变化上是否有解释的可能」。

**采纳。** 技术上完全撑得住：

- 单次计算 **0.33 ms**，几十个情景瞬间出结果；
- 引擎支持 `incoming.effects`（被网、被扰、被中和）与 `buffs`，可以把"被抓住"的状态算进去；
- `state` 组合本身是离散的小空间，只需枚举**有意义的预设**，不做穷举。

**预设情景清单（草案）**：

| 情景 | 含义 |
|---|---|
| `idle` | 全静默（online），不推进不开火 |
| `combat` | 武器 + 推进 + 修复全开（战斗常态） |
| `mwd_on` | 微曲开启：信号半径暴涨、电容消耗剧增 |
| `webbed` | 被网：速度趋零（信号不变） |
| `capped_out` | 电容被抽干：修复与推进失效 |
| `reps_running` | 修复循环中（安甲/遥修）vs 未循环 |
| `no_ammo` | 弹药耗尽 |

输出「**情景矩阵**」：每个情景的关键指标 + 相对 `combat` 基准的 delta。这样「不该输却输了」就有可检验的假设空间，而不是空口猜测。

**必须声明的边界（诚实条款）**：

> 引擎**不建模命中率/伤害应用**（转速 vs 目标角速度、爆炸半径 vs 信号半径）。所以「MWD 开启 → 信号半径 ×5 → 被打得更准 → 有效生存骤降」这条链，工具只能给到「信号半径 ×5」和「EHP 不变」，**后面两步是推理，不是计算**。

这不是缺陷——恰好是分工：工具给可算的分量，agent 给不可算的推理，且必须区分二者。

### 14.6 对前文的修订

- 第 11.4 节「能力画像（capability envelope）」→ 由本节的**多视角**取代；阈值判词降级为可选。
- 第 11.2 节「三态 provenance」保留，但 `state` 的处理方式改为「枚举 + 标注」，不是「标注后不用」。
- 第 12.4 节技能档位结论更新为：默认档 = 全 4 + 补最低要求。

1. **视角清单与字段**定稿（决定工具返回结构）；
2. **情景清单**定稿（决定情景矩阵的形状）；

### 15.1 本轮实测新增发现（影响字段设计）

**发现一：真实抗性可以直接读「正 ID」属性，不必除以权重**

| 层 | 属性 ID | 含义 |
|---|---|---|
| 护盾 | 271/272/273/274 | EM / EXP / KIN / THM 真实共振率 |
| 护甲 | 267/268/269/270 | 同上 |

→ **投影层读正 ID 即可，避免一切权重换算。**（第 12 章的「陷阱二」由此降级为「注意别读错那组」）

**发现二：EVE 属性存在 ×1000 缩放（不止毫秒）**

| 属性 | 原值 | 真实含义 |
|---|---|---|
| `trackingSpeed` | 391.67 | **0.39167 rad/s** |
| `optimalSigRadius` | 40000 | **40 m** |
| `cycleTime` / `reloadTime` / `scanSpeed` / `shieldRechargeRate` | 数千~数十万 | **毫秒** |
| `speed`（武器） | 2226 | 毫秒 |

→ 单位表不是「补一个」，而是**逐字段建表**，且必须单测。

**发现三：弹药是双系伤害，不是单系**

Void S 实测：`kineticDamage 8.9` + `thermalDamage 8.9` → **50/50 动能/热能**。
→ 伤害类型构成必须按「伤害量加权」算，不能按弹种数量。也说明"弹药伤害构成需要知识库"是错的，**SDE 里全有**。

**发现四：`signatureRadius = 385` 说明 MWD 确实处于开启状态**

Hecate 基础信号半径约 90 m，385 ≈ MWD 惩罚后的值。再次证明 `state` 假设会直接改数。

## 16. 第 10 轮：火力视角定稿

### 16.1 裁决结果

| 点 | 裁决 |
|---|---|
| `alpha` vs `volley` | 主人更关注 **`dps`（秒伤）与 `dph`（首轮齐射伤）**。顶层只留这两个；逐武器 `volley` 挂到 `weapons[]` 里做构成拆解 |
| `overload` | **双档都算**（`off` / `on` / `delta`）。场景选择属知识层 |
| `range` | **三档全给**：`optimal` / `optimal+falloff` / `optimal+2×falloff`；导弹另给 `max_range` |
| `ammo_endurance` | 主指标改为**单弹匣时长**（PvP 一般一个弹匣结束战斗），货舱总量降为次要 |
| `application_params` | 首算**只给参数**；能否命中需目标参数**现场对算** |

### 16.2 由此新增的两个设计

**① 过载可持续时间（待验证字段）**

主人指出「远炮热容小容易超坏」。这条**可算**：过载每循环注入 `heatDamage`，热容有限 → 可得出「**能烧多少秒 / 多少循环**」。比"能不能过载"更有用。
状态：需确认 SDE 是否有 rack 级 heat capacity 属性，暂列待验证。

**② 双配装对算接口（结构性需求）**

`application_params` 只给参数，判断命中必须有目标配装 → 需要「攻击方 + 目标方」对算接口。
而目标配装由 agent 猜测/生成/搜索得到 → **生成能力是理解的下游，不是平行功能**。

同时确认：**应用层公式必须自研**（引擎不建模）。公式是公开标准的：
- 炮：hit chance = `0.5^((角速度 × 目标信号半径分母 / 转速 / 目标信号半径)² + 射程超出项²)`
- 导弹：按爆炸半径/爆炸速度 vs 目标信号半径/速度衰减

### 16.3 武器族标签（知识层接口）

代码只给**三个中性数字 + `weapon_family` 标签**（激光 / 混合 / 弹射 / 导弹 / 无人机）。
「激光过失准即无伤、混合残留一丝、弹射偶尔暴击」这类族差异放进知识层，不进代码。

## 17. 第 11 轮：视角二 · 生存

### 17.1 技能约定已验证可用

按「全 4 级 + 补最低要求」自动推导，该配装得到 **19 个技能：17 个 4 级 + 2 个 5 级**（T2 武器技能要求 5）。约定可落地、可复现。

### 17.2 实测结果（全 4 档）

**分层账面：**

| 层 | HP | EM | EXP | KIN | THM |
|---|---|---|---|---|---|
| 护盾 | 650 | 12.5% | 56.25% | 73.75% | 47.5% |
| 护甲 | 840 | 57.5% | **23.5%** | 72.38% | 58.56% |
| 结构 | 2343.75 | 59.8% | 59.8% | 59.8% | 59.8% |

**同一套配装，按伤害类型的总 EHP：**

| 剖面 | EHP |
|---|---|
| 纯动能 | **11347** |
| 纯热能 | 9096 |
| 混合 25/25/25/25 | 8855 |
| 纯电磁 | 8550 |
| 纯爆炸 | **8414** |

> **波动 8414 ~ 11347，相差 35%。** 这就是「单一 EHP 标量」危险的实测证据——同一个配装，遇到不同伤害类型的对手，有效生存差三分之一。

**修复速率语义已确认：**

| 指标 | raw | effective | 校验 |
|---|---|---|---|
| 护甲修复 | 32.5 HP/s | 69.13 EHP/s | 69.13/32.5 = **2.127** = 1/0.470 ✓ |
| 被动盾回充 | 2.031 HP/s | 3.869 EHP/s | 3.869/2.031 = **1.905** = 1/0.525 ✓ |

→ `effective = raw ÷ 该层加权共振率`，**语义确定，可直接进结论**。

**过载档（全过载）：** EHP 不变（此配装无抗性模块可过载）、DPS 365.6 → 420.4（+15%）、护甲修复 32.5 → 42.06（+29.4%）、电容耗尽 28.8s → 25.0s。

### 17.3 三层结构（生存视角的骨架）

| 层 | 内容 | 是否可算 | 归属 |
|---|---|---|---|
| L1 账面 | 分层 HP、分层四系抗性、分层四系 EHP、四系总 EHP | ✅ A 级 | **本视角** |
| L2 修复 | 各层 raw / effective 修复速率、修复依赖（电容/弹药/遥修） | ✅ A 级 | **本视角** |
| L3 对算 | 对具体伤害构型的有效 EHP、有效生存时间、时间曲线 | 需目标 | **对算接口** |

**关键原则：EHP 不作为单值输出。** 单值必然隐含一个伤害剖面假设，而这个假设会把 35% 的差异藏起来。

### 17.4 字段草案

**概览层（默认）**

| 字段 | 内容 | 可信度 |
|---|---|---|
| `layers` | `{shield, armor, hull}` 各自 HP | A |
| `ehp_by_damage` | 四系总 EHP（4 个数） | A |
| `thinnest` | 每层最薄的伤害类型 + 该层 EHP | A |
| `repair` | 各层 `{raw_hp_s, effective_ehp_s}` | A |
| `repair_deps` | 修复是否依赖电容 / 弹药 / 遥修 | A |
| `overload` | 过载后修复与 EHP 的变化 | A |
| `buffer_ratio` | 三层 HP 占比（判断"过盾过甲"打法） | A |

**细节层（按需）**

- 3 层 × 4 系 = 12 个分层 EHP
- 按指定伤害剖面重算的有效 EHP
- 抗性来源拆解（用 `sources`：哪件模块贡献了多少抗性）

### 17.5 可疑点规则（只报事实）

- 某系 EHP 显著低于其他（如本配装护甲爆炸抗性 23.5%，是全船最弱点）；
- 完全无修复能力（纯缓冲）；
- 有修复但电容不稳定（修复无法持续）；
- 结构 HP 占比过高（说明依赖"过盾过甲存活"）；
- 抗性来源集中在单一模块（被打掉即裸奔）。

### 17.6 待主人裁决

1. **四系 EHP 全给（4 个数），还是只给最薄 + 最厚两系**？（前者信息全，后者省 token）
2. **混合 EHP 是否还保留**？（它隐含 25/25/25/25 假设，容易误导；但许多人习惯看这个数）
3. **分层 EHP（12 个数）只放细节层**，概览只给每层 HP + 最薄系——这个颗粒度可以吗？
4. **「有效生存时间」粗算（EHP ÷ (对方 DPS − 修复)）** 放对算接口，不进单配装视角——同意吗？
5. **`repair_deps`**（修复依赖电容/弹药）是否默认输出？它会与"不稳定"视角交叉。

### 17.7 裁决结果与定稿

| 点 | 裁决 | 说明 |
|---|---|---|
| 四系 EHP | **全给（4 个数）** | 理由（主人）：宇宙各地区常用的弹药伤害属性有偏向性，四系分布对**判断场景**有用 |
| 混合 EHP | **保留** | 提供「总血池」的直观第一反应 |
| 分层 EHP | **只给每层多厚**，用混合口径 | 不展开 3×4=12 个数；引擎已直接提供 `-30`/`-28`/`-29` |
| 有效生存时间 | **只在确定对手时给** | 归入对算接口 |
| `repair_deps` | **默认给** | 用了修复装备就要算弹药与电容消耗，属战斗力的一部分 |

**新增知识层条目**：**各地区 / 各族的弹药伤害倾向表**（由第 1 条直接推出）——它是"四系 EHP → 场景判断"的桥梁，属知识而非计算。

**一个必须写进结论的技术提醒**：

> 混合 EHP **不等于**四系 EHP 的算术平均。
> 实测：四系 `[8550, 8414, 11347, 9096]` 算术平均 = **9352**，但混合 EHP = **8855**（差 5.6%）。
> **第 15 轮更正**：当时我写成「等价于四系的调和平均」——**这条是错的**。三层结构下两者都不成立：
> 实测调和平均 = **9219**，与混合值仍差 3.9%。正确算法是按层复算
> `Σ_layer HP_layer / Σ_i(w_i × r_i,layer)`；「等于调和平均」只在单层时成立。
> → 输出时必须标明，避免 agent 拿四个数自己平均。

## 18. 第 12 轮：视角三 · 机动

### 18.1 一个先查清的坑：状态对本视角影响是数量级的

上一轮实验曾得出「状态不影响速度」的错误结论，原因是测试脚本把槽位类型写成 `med`（正确值是 **`medium`**），过滤没有命中任何装备 → 全是空操作。

**这个坑本身要记录**：`slot.type` 的合法值是 `high` / `medium` / `low` / `rig` / `subsystem` / `service` / `fighter_tube` / `fighter_bay` / `implant` / `booster` / `drone_bay` / `cargo`。传错会报错，但**在字符串比较里写错会静默失效**——投影层必须用枚举常量，不能用字面量。

### 18.2 实测：MWD 的三向取舍（Hecate，全 4 档）

| MWD 状态 | 最大速度 | 质量 | 信号半径 | 对齐时间 |
|---|---|---|---|---|
| 无装备 / offline / online | 180 m/s | 1,050,000 | 70 m | 8.04 s |
| **active** | **1059.7 m/s** | 1,550,000 | **385 m** | **11.86 s** |
| **overload** | **1499.5 m/s** | 1,550,000 | 385 m | 11.86 s |

换算成倍数（active 相对 online）：

- 速度 **×5.89**
- 信号半径 **×5.5**（70 → 385，即 +450%）
- 对齐时间 **+47.6%**（质量 +500,000）

> **这就是机动视角最有价值的一条**：开 MWD 不是单纯"变快"，而是**速度 ×5.9 换 信号半径 ×5.5 与 对齐 +48%**。而信号半径直接影响被命中概率（应用层）——「开了微曲反而被打得更准」是可算的事实链，不是玄学。

同时暴露出一个 EVE 的经典矛盾，工具可以原样呈现：**开 MWD 时对齐时间变长**（想跑更快，但更难转向脱出）。三个数一起给，agent 自己就能看到。

**对齐时间公式已复算验证**：`alignTime = -ln(0.25) × agility × mass / 1e6`，实测 11.8611 与引擎完全一致。

### 18.3 字段草案

**概览层**

| 字段 | 内容 | 可信度 |
|---|---|---|
| `speed` | 最大速度（当前状态） | A |
| `align_time` | 对齐时间（秒） | A |
| `signature_radius` | 信号半径（m） | A |
| `mass` / `agility` | 用于解释速度与对齐的来源 | A |
| `warp_speed` | 跃迁速度 | A |
| `propulsion_states` | **三态对比**：`off` / `active` / `overload` 下的速度、信号、对齐 | A |

**细节层**：推进模块类型与尺寸、是否有跃迁加速/减速影响、热损累积。

### 18.4 可疑点规则（只报事实）

- 无推进模块（不具备脱离能力）；
- 对齐时间过长（相对信号半径与速度的组合）；
- 开推进后信号半径过大（被命中概率上升）；
- 速度高但对齐慢（能跑直但不便转向脱离）。

### 18.5 待主人裁决

1. **`propulsion_states` 三态对比默认给吗？**（我认为必须给，它是本视角的核心；成本 +0.7ms）
2. **是否给「被抓风险」的定性判词**，还是只给数字（对齐 11.9s、信号 385m）让 agent 判断？按前面定的原则应只给数字。
3. **`warp_speed` 与起跳相关字段**要吗？（跃迁速度、跃迁核心稳定）
4. **被网 / 被扰后的速度**属对算接口，还是机动视角也做一个情景？（会与情景枚举重复）

### 18.6 裁决结果与定稿

| 点 | 裁决 |
|---|---|
| `propulsion_states` 三态 | **默认给**（`off` / `active` / `overload`） |
| 定性判词 | **不给**，只给数据，具体场景具体分析 |
| 跃迁相关 | **要**——与「进场时间」有关，场景分析需要 |
| 被网 / 被扰 | **归对算接口**：不同装备的网结果不同，有目标才有分析 |

**「进场时间」拆解**：`进场时间 = 对齐时间 + 跃迁飞行时间`。

- 对齐时间：引擎直接给 `-1`，公式已复算验证；
- 跃迁飞行时间：**引擎不给，需自研**（由 `warpSpeedMultiplier`、距离、质量/敏捷决定）。公式公开，但属"要自己写且要测"的部分。
- → 单配装视角只给 `warp_speed` 与对齐时间；「到 X AU 外需要多久」作为可选计算字段（标注为估算）。

## 19. 第 13 轮：视角四 · 资源

### 19.1 实测底数（Hecate，全 4 档）

| 项 | 输出 | 负载 | 余量 |
|---|---|---|---|
| CPU | 276.0 | 287.0 | **−11.0** |
| PowerGrid | 64.8 | 72.0 | **−7.2** |
| 标定（rig） | 400.0 | 225.0 | +175.0 |

槽位：高 6 / 中 4 / 低 4 / rig 3（已用情况：高 6、中 3、低 3、rig 3，另空 1 中 1 低）
炮台挂点剩余：5（`turretSlotsLeft`）
货舱：容量 328.05

**这套配装在全 4 档下 CPU 与 PG 都不够。** 这正是第 14.4 节那条措辞约束的现实证据：

> 说「这套配装非法」是错的（换成全 5 或加植入体就能飞）；
> 说「全 4 档下 CPU 超 11.0、PG 超 7.2」才是准确且可行动的。

### 19.2 字段草案

**概览层**

| 字段 | 内容 | 可信度 |
|---|---|---|
| `cpu` | `{output, load, free}` | A |
| `powergrid` | `{output, load, free}` | A |
| `calibration` | `{output, load, free}` | A |
| `slots` | 高/中/低/rig：`{used, total}` | A |
| `hardpoints` | 炮台 / 发射器挂点剩余 | A |
| `drone_resources` | 带宽 `{used, total}`、容量 `{used, total}` | A |
| `cargo` | `{used, total}` | A |
| `empty_slots` | 空槽位清单（哪一类、几个） | A |

**细节层**：逐装备资源消耗排行（哪几件吃掉了大部分 CPU/PG）、弹药容量与装填量。

### 19.3 可疑点规则（只报事实）

- 余量为负（该技能档下装不下）；
- 余量极低（任何改装都会溢出）；
- 余量极大而槽位空置（资源浪费，且说明没装优化件）；
- 无人机带宽有余量但未携带无人机；
- 货舱容量与弹药/消耗品需求矛盾。

### 19.4 待主人裁决

1. **余量给「相对百分比」还是「绝对值」**，还是都给？
2. **`empty_slots` 要不要列出具体类别**（高/中/低各空几个），还是只给一个总数？
3. **是否给「可换装空间」提示**（如"CPU 余 175 可换装更高 meta"）？按前面原则应不给（那是生成的活），但这条与资源视角关系最近。
4. **资源视角是否也要三态/过载对比**（过载会改变部分资源属性）？

### 19.5 裁决结果

| 点 | 裁决 |
|---|---|
| 余量 | **绝对值**（不给百分比） |
| `empty_slots` | **具体到类别**（高/中/低/rig 各空几个） |
| 可换装空间 | **给**。理由（主人）：有了余量数据，agent 可以自行推演「加钱换更强装备会怎样」，能得出很多更有趣的结果 |

### 19.6 「可换装空间」的实现路径

要回答「这个槽位还能升级到什么」，需要三样东西：

1. 同组装备清单（按 `metaLevel` 排序）；
2. 每件候选的 CPU / PG / 标定消耗；
3. 换装后重算一次（引擎，0.33 ms）。

→ 这不是生成配装，只是「**能不能装下**」的可行性枚举。判断「该不该换」仍交给 agent。

### 19.7 重要架构发现：引擎没有查询能力

实测 `dir(esf_dogma_engine)` 的全部公开接口：

| 类型 | 接口 |
|---|---|
| 计算 | `calculate`、`beacon` |
| 读取 | `load_eft` / `load_dna` / `load_killmail` / `load_esi_fitting` / `load_esf` / `load_link` |
| 写出 | `save_eft` / `save_esi_fitting` / `save_esf` / `save_esf_link` |
| 数据 | `load_sde` / `load_names`、`post_load` |
| 类型定义 | `Fit` / `Calculation` / `Violation` 等 TypedDict |

**没有任何 type / group / attribute 的查询接口。** `eveshipfit_sde` 也只提供文件路径与 build number。

→ 结论：**必须自建一个 SDE 索引库**（否则做不到名称搜索、同组候选、单位表）：

| 需要的能力 | 仅靠引擎 | 需要索引库 |
|---|---|---|
| 计算 | ✅ | — |
| 格式互转 | ✅ | — |
| type_id → 名称（含中文） | ❌ | ✅ |
| 名称 → type_id（模糊/多语言搜索） | ❌ | ✅ |
| group → 同组装备 + metaLevel | ❌ | ✅ |
| attribute_id → 名称 / 量纲 | ❌ | ✅ |

**已验证的数据来源**：

- ESI `?language=zh` 可取中文名（实测：`Light Neutron Blaster II` → 「轻型中子疾速炮 II」）；
- ESI `/universe/groups/74/` 实测返回 228 个 type（Hybrid Weapon 组）；
- ESI `/dogma/attributes/{id}/` 返回 `name` / `display_name` / `description` / **`unit_id`**（部分属性有）/ `high_is_good`。

**但有一个坏消息**：`trackingSpeed` 的 ESI 记录**没有 `unit_id`**，而它的值又是 ×1000 缩放的（391.67 实为 0.39167 rad/s）。
→ **量纲可以从 SDE 取，缩放系数仍必须手工维护一张小表**，且要单测。这条是"自建索引也解决不了"的残留风险。

### 19.8 待补答

第 4 点主人未答：**资源视角是否也要三态/过载对比？**（过载会改变部分资源属性，但影响面小于火力/机动）

## 20. 第 14 轮：视角五 · 约束

### 20.1 本视角的核心：把「违规」拆成两类

这是约束视角唯一真正重要的设计——两类违规的**处置方式完全不同**：

| 类别 | 含义 | 例子 | agent 该做什么 |
|---|---|---|---|
| **硬违规** | 配装本身错，换技能也救不了 | 弹药组不匹配、rig 尺寸错、槽位冲突、子系统冲突、船体限制 | 改配装 |
| **档位违规** | 当前技能档下装不下，换档/加植入体可解 | CPU / PG / 标定不足、技能等级不足 | 挂号技能 / 换低配 |

把这两类混在一起报，agent 只能瞎猜；分开报，下一步动作是明确的。

### 20.2 引擎已提供的违规类型（实测字段）

`resource`（cpu / powergrid / calibration / drone_bay / drone_bandwidth / launched_drones / fighter_* / cargo_bay / charge_capacity）、`slots`、`wrong_slot`、`slot_taken`、`wrong_slot_index`、`subsystem_taken`、`skill`、`rig_size`、`ship_restricted`、`capital_item`、`max_group`、`max_type`、`charge_group`、`charge_size`。

分类映射：`resource` + `skill` → 档位违规；其余 → 硬违规。

### 20.3 字段草案

| 字段 | 内容 | 可信度 |
|---|---|---|
| `hard_violations[]` | 与技能无关的违规（原样 + 人话描述） | A |
| `tier_violations[]` | 当前档位下的资源/技能缺口（含具体数值） | A |
| `skill_requirements[]` | 每个模块要求的技能 + 等级 | A |
| `skill_gap` | 当前档位相对全部要求的缺口（缺哪些、差几级） | A |
| `needs_implant` | 全 5 档仍不足时提示「可能需要植入体」 | A（推断） |

### 20.4 待主人裁决

1. **「硬违规 / 档位违规」二分**是否认可？这是本视角的骨架。
2. **技能要求是全量列出**（每个模块都列）还是**只列缺的**？
3. **`needs_implant`** 要不要给？（逻辑：全 5 档仍超载 → 可能依赖植入体；但植入体本身不可知，只能提示）
4. **是否要算「刚好能飞的最低技能档」**？——即求出「在 CPU/PG 不超的前提下，最低需要各技能几级」。这比"全 4"更直接回答"我还得挂多少技能"，但需要一个小规模搜索（只涉及 4 个影响资源的技能，成本很低）。

### 20.5 裁决结果与定稿

| 点 | 裁决 |
|---|---|
| 违规二分 | **认可**：硬违规 / 档位违规 |
| 技能要求全量 vs 只列缺 | 两者都不对。**纯静态模拟没有玩家技能数据，谈不上"缺"**。正确输出：客观的「配装门槛清单」+ 假设档下是否满足 |
| `needs_implant` | **要**（提示需要植入体支持） |
| 最低技能档求解 | **不做**；改用零成本的**聚合画像** |

**技能门槛画像 `skill_floor`**（替代求解）：

```
{ max_level: 5, count_L5: 12, count_L4: 3, count_L3: 1, distinct_skills: 16 }
```

由各模块 `requiredSkill1..6` + 等级直接聚合，不搜索、不重算，token 消耗可忽略。
（第 15 轮更正：技能 ID **不连号**——1/2/3 = 182/183/184，4/5/6 = **1285/1289/1290**；等级 1/2/3 = 277/278/279，4/5/6 = 1286/1287/1288。185/186/280/281 是别的属性，别再抄。）

**"技能要求"的正确定位**（本轮澄清）：它不是"玩家缺什么"（我们不知道），而是**配装本身的属性**——这套配装要求驾驶员多强。用途：判断交易门槛、反推 killmail 中对手的技能水平。

### 20.6 视角六 · 不稳定 定稿

| 点 | 裁决 |
|---|---|
| `cap_sensitivity` | **要** |
| 稳定临界点（逆问题） | 不用 |
| `consumables` 与 `repair_deps` | **合并**：消耗品续航归本视角，生存视角只保留修复速率 |

**补充事实**：超载不改变 CPU/PG/标定（已确认），但**会改变电容消耗**——实测耗尽时间 28.8s → 25.0s。所以"过载不影响资源"成立，"过载不影响电容"不成立。
