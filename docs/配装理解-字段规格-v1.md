## 0. 全局约定

### 0.1 返回分级

| 级别 | 何时返回 | 体量目标 |
|---|---|---|
| `overview` | 默认 | 每视角 5–10 个字段；**实测六视角合计 13,519 chars（≈4–5k token）**，预算上限 17,000 chars，默认不降级 |
| `detail` | 显式请求某视角或某字段 | 按需展开 |
| `explain` | 请求某指标归因 | 走引擎 `sources`，限深 2 层 |

> **原估「全视角 800–1500 token」已被实测推翻**（差了约 3 倍），根因是 provenance 逐叶子覆盖 + 资源视角字段多。
> 体积压缩（provenance 聚合 / detail 下沉）列在 P3 处理，不在 P2 范围。

### 0.2 值来源三态（每个数值字段必带）

| 态 | 含义 |
|---|---|
| `measured` | 由输入直接决定，且**不随技能档 / 模块状态 / 模式 / 伤害剖面变化** |
| `assumed` | 依赖上述任一假设（技能档、状态、模式、剖面、装填） |
| `unknown` | 无法推断，且**不用默认值冒充** |

> **重要区分（第 16 轮裁决，此前规格把两者混在一起过）**
> 本文档 §1–§6 各表里的「可信度」列（A / B / C / D / E）**不是 provenance**，两者是正交维度：
>
> - **可信度**：我们对该数值**口径**的把握（A=已对拍、B=需换算、C=不可用、D=需对拍、E=未建模）
> - **provenance**：该数值在**本次计算**里是否依赖假设
>
> 例：`dph(-11)` 的可信度是 **A**（口径已实测），但 provenance 是 **assumed**（依赖技能档与弹药假设）。
> **provenance 的权威来源是投影层**（`project/provenance.py`），且该表最终由实测推导（见 `tools/derive_provenance.py`），不要从本文档反推。

### 0.2.1 `unknown` 必须带原因（第 20 轮裁决 = 方案 A）

三态**不变**（保住 36 样本 / 1548 字段的验收基线），但每个 `unknown` 叶子额外带一条 **`reason`**，因为同一个 `unknown` 实际装着四种完全不同的情况：

| `reason` | 含义 | 真实例子 | agent 该怎么处置 |
|---|---|---|---|
| `input_incomplete` | **输入数据不完整** | f4 的 `dph: null`（killmail 不带 mutation） | 换途径补数据，或降低置信度 |
| `not_applicable` | **该字段对本配装不适用** | 炮船的 `application.explosion_radius_m`（没导弹） | 直接忽略 |
| `ambiguous` | **无唯一答案** | `thinnest.hull.damage_type`（四系抗性并列） | 说“四系相同”，不是“不知道” |
| `engine_omits` | **引擎永不提供** | `-70 maxTargets`（恒缺） | 别用这个字段 |
| `unclassified` | 兜底（**应为 0，出现即待补规则**） | — | 视为缺陷上报 |

**输出形态**：平行稀疏表，只在 `provenance == unknown` 的路径上出现：

```json
"views": {"firepower": {
  "overview": {...},
  "provenance": {"dph": "unknown"},
  "unknown_reasons": {"dph": "input_incomplete"}
}}
```

**判定优先级**（实现时按此顺序，命中即停）：

1. 有 flag 直接解释该字段（如 `weapon_damage_zero` → `input_incomplete`）
2. 该字段在规格里是**条件字段**（§0.6 与各视角表标注的） → `not_applicable`
3. 来源属性在「引擎永不提供」清单（`-70` 等） → `engine_omits`
4. 该字段的语义是「在多值中选一个」且并列 → `ambiguous`
5. 否则 → `unclassified`（**必须报为缺陷**，说明缺一条规则）

### 0.3 单位约定

- 字段名带单位后缀：`_s`（秒）、`_m`（米）、`_pct`（百分比）、`_mps`（米/秒）。
- 内部一律换算到**秒 / 米 / 百分比**，不输出毫秒与 ×1000 缩放值。
- 已知缩放（实测）：`cycleTime`/`reloadTime`/`scanSpeed`/`shieldRechargeRate` 为毫秒；`trackingSpeed` 与 `optimalSigRadius` 为 ×1000。

### 0.4 视角原则

每个视角**只输出事实、边界、可疑点**；不汇总、不评分、不排名、不给定性判词。

### 0.5 默认假设（全部记为 `assumed`）

| 项 | 默认值 |
|---|---|
| 技能档 | 全部技能 4 级，逐模块补到 `max(4, required)` |
| 模块状态 | 引擎导入规则（武器/推进/修复 active） |
| 伤害剖面 | 25/25/25/25，但**不作为唯一 EHP 输出** |
| 装填 | 满弹匣 |
| 植入体 | 无（不可知） |

### 0.6 输入保真 —— `unknown` 的主要来源

> **输入本身不完整时，数值不可信。必须输出 `null` + `unknown` + 显式 flag，不得给出 `0.0` 或任何「看起来合理」的值。**

已确认的三类不完整输入（全部由真实 KB 样本撞出来的）：

| 类别 | 例子 | 后果 |
|---|---|---|
| **突变数据缺失** | killmail 不带 Abyssal/mutated 的 `mutation` | 导弹伤害**归零**（`-11/-12/-21` 全 0）、推进速度**无加成**（Abyssal AB 的 `speedFactor` 1.0 vs 正品 135.0） |
| **状态未知** | killmail 不带 module `state` | 资源占用按「全 active」算，可能把**不可能在线**的模块计入（实测 Loki：理论 10572 tf vs 真实可飞 472 tf） |
| **舱内存放被丢弃** | `load_killmail` 静默丢弃 flag 177（SubSystemBay） | 子系统加罚/减免判定错误（T3C 的 covert cloak 被加 10000 罚值） |

**判据写进代码的是「自相矛盾」，不是模块类型穷举**：
- 有带弹药的武器，但 `dph == 0` → `dph` 输出 `null` + `unknown` + flag `weapon_damage_zero`
- `cpu.load > cpu.output` 且模块 `state` 为 active/online → 标 `feasible = false`，并提示「部分模块在真实游戏中不可能在线」

**为什么不用「检测 Abyssal 类型」**：模块类型会随版本增加，而**矛盾条件不会**——有弹药却零伤害、超预算却全额计费，这类矛盾永远意味着输入或状态有问题。

| `hardpoints_free` | `{turret, launcher}` | 102 + 空槽统计 | measured | |

- 每武器组：`cycle_time_s`、`volley`、`damage_per_cycle`、弹药四系伤害
- 热：每循环热损、**过载可持续时长**（原料已确认齐全，见下）
- 无人机 / 战斗机：DPS 与带宽占用

## 2. 视角二 · 生存 `survivability`

### overview

| 字段 | 类型 | 来源 | provenance |
|---|---|---|---|
| `layers` | `{shield_hp, armor_hp, hull_hp}` | 263 / 265 / 9 | measured |
| `layer_ehp` | `{shield, armor, hull}` | `-30` / `-28` / `-29` | measured |
| `ehp_by_damage` | `{em, explosive, kinetic, thermal}` | 由 267–274 / 109–113 与分层 HP 计算 | measured |
| `ehp_mixed` | number | `-43` | measured |
| `thinnest` | 每层最薄系 + 该层 EHP | 同上 | measured |
| `repair` | `{layer: {raw_hp_s, effective_ehp_s}}` | `-45/-48`、`-47/-50`、`-46/-49`、`-51/-52` | measured |
| `overload` | 修复与 EHP 的过载变化 | 重算 | measured |

**强制说明**：`ehp_mixed` **既不等于** `ehp_by_damage` 四值的算术平均，**也不等于**其调和平均（多层结构下两者都不成立）。
实测：混合 **8855** / 算术 **9352** / 调和 **9219**。
正确算法必须按层复算，不能取平均：

```
ehp_mixed = Σ_layer  HP_layer / Σ_i ( w_i × r_i,layer )
```

输出必须标明「混合 EHP 不是四系平均」，避免 agent 自行平均。

### detail

- 抗性矩阵 3 层 × 4 系（真实共振率，读正 ID：267–274 / 109–113）
- 抗性来源拆解（`sources`）
- 按指定伤害剖面重算

> 消耗品续航**不在本视角**，已归入「不稳定」。

| 字段 | 类型 | 说明 |

## 10. 新发现的维度：模式（stance）

Hecate 的属性里发现一整套模式相关字段：

| 属性 | ID | 值 | 含义 |
|---|---|---|---|
| `stanceSwitchTime` | 1985 | 10000 | 模式切换耗时（ms） |
| `shipBonusTacticalDestroyerGallente1/2/3` | 2027/2028/2029 | −3 / 7.5 / −5 | 三种模式的船体加成 |
| `proximityDbuffEffectTacticalDestroyerHP` | 6270 | 0 | 模式相关 dbuff |

**含义**：有模式的船（T3D / T3C），**同一套配装有 N 种表现**，而 killmail 不带模式信息。

→ 结论：**`mode` 必须作为情景维度**，与 `state` 并列。引擎支持 `fit.ship.mode = <type_id>`（不校验归属），可直接枚举。

`mode` 应加入的范围：

- 火力视角：不同模式的伤害 / 射程
- 生存视角：不同模式的抗性
- 情景矩阵：`mode` × `state` 的组合（只取有意义的组合）

**副产品**：发现一组对「被扰」对算有用的属性——
`energyWarfareResistance` 2045、`sensorDampenerResistance` 2112、`weaponDisruptionResistance` 2113、`stasisWebifierResistance` 2115（Hecate 全为 1.0，即无抵抗）。这些正好是对算接口里"被网 / 被扰"的输入。

### 10.1 模式已定位（实测，2026-10-18）

模式是**独立的 type**，全部位于 **group 1306**，且为 `published=false`（ESI 不可见）。

Hecate 的三个模式：`35686 Defense` / `35687 Propulsion` / `35688 Sharpshooter`。

模式 type 自带修饰属性（Defense 为例）：`mode{Em,Explosive,Thermic,Kinetic}ResistancePostDiv = 1.5`、`modeArmorRepDurationPostDiv = 1.5`。
→ 语义为"共振率 ÷ 1.5"，已由引擎结果反证。

### 10.2 实测影响：模式比 state 影响还大

同一套 Hecate（一门中子炮），**技能档 `all4+min_required`（512 技能）**、SDE 3607705：

| 模式 | EHP | DPS | 对齐时间 |
|---|---|---|---|
| 无模式 | **4609.69** | **66.32** | **6.428** |
| **Defense** | **6264.53（+35.9%）** | 66.32 | 6.428 |
| **Propulsion** | 4609.69 | 66.32 | **2.143（−66.7%）** |
| **Sharpshooter** | 4609.69 | **88.43（+33.3%）** | 6.428 |

> **旧值作废**：曾经记录的 `4530.9 / 47.68 / 8.04` 与 `63.58` 是在一套 15 技能集下测的，与默认档不可比（见 `回归快照-changelog.md`）。
> **技能档变了，快照必须重测**——这是本项目已经踩过两次的坑。

**结论**：

1. `mode` 必须作为**默认假设项**记录（killmail 不带模式信息 → `assumed`/`unknown`）；
2. 默认输出「无模式」的数值，并**附三模式对比**（成本约 1 ms，收益极大）；
3. 有模式的船（T3D / T3C），六视角中火力、生存、机动三个视角都受模式影响。
