# 输出分层与工具集 v1

> 背景：P2 结束时 `render_overview` 对最复杂样本实测 **23,256 字符**（紧凑序列化）。
> （此前文档写的 29,213 是**带 `indent=1` 缩进**的字符数，属于重复计费，已修正。）
> `views` 16,723 + `meta` 6,439，其中 `assumptions.skill_tier` 的 512 条占 6,007。
> 一份"概览"约 7,000 token，30 条船的 BR 就要 20 万 token —— **不可用**。
>
> 结论：不是"再省几个字节"，而是**同一个结果要按消费者需要分层提供，并拆成多个可单独调用的工具**。

---

## 1. 分层契约

| 层 | 工具 | 内容 | 体量目标 | 谁用 |
|---|---|---|---|---|
| **L0 摘要** | `fit_index` | 六维度每视角 3–5 个数 + 精简 flag + provenance **计数** | **≤ 2,500 字符**（实测 1,722–1,987） | 默认。批量看战报、快速判断 |
| **L1 视角** | `fit_view(view)` | 单视角全字段 + 该视角 `provenance` / `unknown_reasons` / `confidence` / 带 evidence 的 flags | 2,000–3,500 | 发现某维度可疑，展开看 |
| **L2 明细** | `fit_detail(view, path?)` | 全量列表（升级候选、逐模块电容、逐武器） | 按需 | 深度分析 |
| **归因** | `fit_explain(metric)` | 某数值由哪些属性/模块贡献 | 按需 | 「为什么这么高」 |
| **任意取数** | `fit_get(path)` | 按稳定路径取任意节点（含 L0/L1/L2） | 极小 | agent 精确取一个数 |

**关键约束：`fit_get(path)` 的路径表达式在 L0/L1/L2 里一致** —— agent 从 L0 看到 `mobility.speed_mps`，就能直接 `fit_get("mobility.speed_mps")`。

---

## 2. 三张平行表的去向

| 表 | L0 | L1 | L2 |
|---|---|---|---|
| `provenance` | **只给计数** `{measured: n, assumed: n, unknown: n}` | 逐叶子路径 → 状态 | 同 L1 |
| `unknown_reasons` | **只给计数** `{not_applicable: n, ...}` | 逐叶子路径 → 原因 | 同 L1 |
| `confidence` | **只给非 A 的条数** | 稀疏表 | 同 L1 |

> 理由：L0 的读者是"要不要继续看"，不是"每个数可不可信"。逐叶子置信度属于 L1。

## 3. L0 字段清单（每视角 3–5 个）

### 火力
- `weapons` —— `{count, families: []}`（不列名字）
- `dps_base` / `dph`
- `range_m` —— `{optimal, max}`（无导弹则只给 optimal）
- `damage_split` —— 四系比率（和为 1）

### 生存
- `ehp_mixed`
- `layers` —— `{shield, armor, hull}` 三层 HP
- `thinnest` —— `{layer, damage_type}`（最薄的一层与伤害类型）
- `repair_total_hp_s` —— 三层修复速率之和（0 也照给）

### 机动
- `speed_mps` / `align_time_s` / `signature_radius_m`
- `propulsion_state` —— 当前用的是哪个推进档（`active` / `propulsion_off` / `off`）

### 资源
- `cpu` / `powergrid` —— `{load, output, free}`
- `feasible` —— bool
- `slots` —— `{high: "3/6", medium: "5/5", low: "3/3", rig: "2/2"}`

### 约束
- `hard_violations` —— `{count, kinds: []}`（如 `["max_group"]`）
- `tier_violations` —— `{count, kinds: []}`（如 `["resource"]`）
- `needs_implant`

### 不稳定
- `cap_stable_pct` / `cap_depletes_in_s`
- `cap_load_gj_s` / `cap_recharge_gj_s`
- `has_external_dependency`

### 顶层
- `ship` —— `{name, group, type_id}`
- `meta` —— `{sde_build, engine_version, spec_version, skill_tier: {name, count}, module_states, damage_profile, mode}`
- `flags` —— `[{id, hint}]`（**不带 evidence**；`hint` 为 6–10 字摘要，从 evidence 生成，无 evidence 时为 `null`）
- `provenance_counts` —— 每视角 `{measured, assumed, unknown}`
- `budget` —— `{chars, degraded}`

## 7. 红线（沿用既有）

- L0 **不得**包含 `evidence`、逐叶子 provenance、逐模块列表
- L0 的每个数值**必须**能在 L1 里找到同名路径（保证 `fit_get` 可用）
- `degraded` 若为 true，**必须在 L0 显式出现**（不能让读者以为看到了全部）
- L0/L1/L2 三层对同一字段的**数值必须逐位相同**（由测试钉住）

## 8. 验收后裁决（第一次 L0/L1 验收回执）

验收方实测后提出 6 处文档↔实现冲突，逐条裁决如下（**文档为准，实现按此改**）：

| # | 冲突 | 裁决 |
|---|---|---|
| **C1** | 文档写 L0 ≤ 1,500，实测 1,722–1,987（65/65 超） | **改为 ≤ 2,500**。原 1,500 是我的估算（按 6 视角×4 字段），实测三处系统性低估：flags 实际 6–7 条（我按 2 条估）、字段名+真实数值压不动、`meta` 含 `module_states`/`damage_profile`。2,500 仍比旧输出 23,256 低 **89%**，护栏意义不变 |
| **C2** | 文档 `flags={id,message}`，实现只给 `{id}` | **改为 `{id, hint}`**：message 太长（f47 七条合计 688 字符）过不了预算；但只有 id 又猜不出含义 → 取 6–10 字 `hint`，从 evidence 生成 |
| **C3** | 文档 `provenance_counts` 是对象，实现是无标签数组 `[2,9,19]` | **改回带标签对象** `{measured, assumed, unknown}`。未标序的数组对 agent 是**隐藏契约**，多花约 200 字符值得 |
| **C4** | 文档要求「L0 字段能在 L1 找到**同名**路径」，实现用别名（`dps_base` vs `dps.base`） | **保留别名，但必须显式登记**：`INDEX_SPEC` 里每个别名都要写「底层路径」，`get_path` 两种写法都接受。见 §9 别名表 |
| **C5** | 文档未标 nullable，实现有 6 个样本给 `null` | **文档补 nullable 标注**：`dps_base` / `cap_load_gj_s` / `cap_depletes_in_s` / `damage_split` / `range_m.optimal` 在对应条件缺失时为 `null` |
| **C6** | `budget.chars` 不含 budget 块自身（差约 46） | **接受并注明**：`chars` 统计的是**预算内正文**，不含 `budget` 块本身 |

### 8.1 第一次验收的结论分布

| 项 | 结果 |
|---|---|
| 旧 `render_overview` 基线 | **2,860/2,860 字段全齐**，但新增 2 条 provenance 错误（`unclassified`）→ blocker |
| L0 契约 | 通过（字段按文档独立核对 44 项全在、红线 0 违反、1,190 个数值叶子全部可 `get_path` 取回且逐位相同） |
| L1 一致性 | 通过（未降级样本 390/390 视角逐字节相同；flags 带 evidence 0 缺） |
| `get_path` | 通过，但有 968 处 `provenance: null`（别名未解析）→ medium |
| L0 可用性 | 验收方建议加 `hint`、压缩 `damage_split`/`meta` → 采纳 |

### 8.2 暴露的一个教训

> **新层做对了，旧层被碰坏了。**

T-37 为了让「有值就不再说不适用」而删掉条件登记，结果**值为 `None` 的样本**失去了 reason 覆盖 → `unclassified`。
→ **删除一条规则前，必须先枚举「这条规则当前在哪些样本上生效」**，而不是只想着「现在有值了所以用不上」。

## 9. L0 别名表（必须显式登记）

| L0 字段 | 底层路径（L1） | 说明 |
|---|---|---|
| `firepower.dps_base` | `firepower.dps.base` | |
| `firepower.range_m.optimal` | `firepower.range.optimal_m` | |
| `firepower.weapons.count` | `firepower.weapons[].count` 聚合 | 聚合值 → provenance `assumed` |
| `firepower.damage_split` | `firepower.damage_split` | **保持四键结构，无武器时四值均为 `null`**（不整块给 `null`，见 §8.3） |
| `survivability.layers.shield` | `survivability.layers.shield_hp` | 同理 armor / hull |
| `resources.cpu.*` / `powergrid.*` | 同名三层结构 | |
| `provenance_counts.*` | 由 L1 的 `provenance` 表计数得出 | 无单一底层路径 |

**要求**：`get_path("firepower.dps_base")` 与 `get_path("firepower.dps.base")` **都要能取到同一个值**，且都带 `provenance`。
### 8.3 撤回一条改动：`damage_split` 保持四键结构

第一次实现时曾把「四系全 `null`」压成整块 `null`（省约 30 字符）。**已撤回**，理由：

| 考虑 | 判断 |
|---|---|
| 形状稳定性 | `dict ↔ null` 是**形状多态**，比「值多态」更危险 —— 消费方每次都要先判类型。<br>而 `range_m.optimal`、`weapons.families` 这些既有字段都是**形状恒定、值可变**。 |
| 省下的成本 | 仅 ~30 字符/样本（占 1.7%），换来的风险不值得 |
| 语义表达 | 四键全 `null` 已经足够表达「无武器、四系伤害不适用」，不需要换成整块 `null` |

**规则**：L0 的**字段形状必须恒定**（对象永远是对象、数组永远是数组）；可变的是**值**，不是形状。

> 这条同时提醒：改输出形状前，必须先看**验收脚本与下游消费方**是否依赖该形状 —— 形状是契约，值是数据。
