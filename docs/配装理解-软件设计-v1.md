## 0. 我对需求的理解（请重点核对）

1. **这是"给 agent 用的理解层"，不是给人用的界面**。人不直接消费它，agent 消费它，然后由 agent 组织叙事。
2. **数值必须由代码算，agent 只做选择、解释与叙事**。任何让模型直接"读原始数据下结论"的路径都会变成幻觉生成器。
3. **六个视角各自独立，互不汇总**。输出事实、边界、可疑点，不输出"这套好不好"。
4. **一切数值必须可溯源**：能回答"这个数是哪来的"（三态 provenance）、"为什么是这个数"（`sources` 归因）。
5. **计算引擎是别人的，我们不重写**；但**查询、投影、知识、接口全是自己的**——因为引擎只做计算+格式转换，没有任何 type/group/attribute 查询能力。
6. **本期不做生成与战报**，但读取/理解的结构要能承接它们（对算接口、情景矩阵、目标配装都是下游）。

若以上有偏差，架构需要改；若一致，下面的分层就是结论。

## 2. 组件职责与边界

| 层 | 组件 | 职责 | 明确不做 |
|---|---|---|---|
| L1 | SDE Ingestor | 比对 build 号、下载、解析、建索引 | 不做游戏逻辑 |
| L1 | 索引库 | types/groups/meta/属性字典的查询 | 不存计算结果 |
| L1 | 属性字典 | 属性 ID→名称/量纲/**缩放规则** | 不含业务判断 |
| L2 | Engine Adapter | 封装引擎：加载一次、计算、格式互转、validate | 不重写 dogma |
| L2 | Fit Normalizer | 任意输入→`type_id` 统一结构；输出**可修复错误** | 不猜歧义（宁可报错） |
| L2 | Assumption Engine | 技能档（全4+补最低）、state、mode 推定并记录 | 不隐藏假设 |
| L2 | Scenario Runner | 批量变体计算、并行 | 不定义"哪些情景有意义"（规则外置） |
| L3 | 单位与缩放 | 全部转成 秒/米/百分比 | 不输出毫秒、×1000 原值 |
| L3 | 六视角抽取器 | 每视角 overview/detail 字段 | 不跨视角汇总 |
| L3 | provenance 标记器 | 每值三态 | 不用默认值冒充 unknown |
| L3 | 可疑点规则引擎 | 事实性异常提示 | 不做好坏判词 |
| L3 | 归因引擎 | `sources` 限深展开 | 不解释到单条 modifier 之外 |
| L3 | 分级渲染 | token 预算内组织返回 | 不替 agent 写结论 |
| L4 | 知识层 | 解释与场景判断的参考 | **绝不参与数值计算** |
| L5 | MCP/CLI | 参数→结果 | 不做 NL、不做叙事 |
| L5 | Skill | 规程与表述纪律 | 不承载"必须保证"的约束 |

## 3. 关键数据流

### 3.1 读取

```
调用方拿到 EFT 文本
  → fit_read(text)
      ├─ 判定形态（EFT / DNA / ESI / killmail / 结构化）
      ├─ 归一化为 type_id 结构
      ├─ 失败 → 可修复错误 {line, raw, failed_at, candidates[], reason}
      └─ 成功 → Assumption Engine 标注技能档 / state / mode / 剖面
  → 返回 {fit, assumptions[], unknown[], warnings[]}
```

### 3.2 理解

```
fit_understand(fit, views=[...], tier="overview")
  → 对每个视角：
      ├─ 取引擎计算所需变体（Scenario Runner 按需计算）
      ├─ 抽取器读属性 → 单位换算 → 三态标记
      ├─ 可疑点规则匹配
      └─ 按 tier 渲染
  → 返回 {views: {...}, meta: {sde_build, engine_version, spec_version, assumptions}}
```

### 3.3 归因与灵敏度

```
fit_explain(fit, metric)     → sources 链，限深 2 层
fit_sensitivity(fit, ...)    → 逐模块关闭 / state 切换 / mode 切换 → 指标 delta
```

## 4. 关键设计决策（含理由）

| # | 决策 | 理由 |
|---|---|---|
| D1 | 计算全权交给 `eveshipfit-dogma-engine`，不重写 dogma | 引擎已实测正确（堆叠惩罚、抗性对拍 12/12），自研必错 |
| D2 | **自建 SDE 索引库** | 引擎无任何查询能力（已实测 `dir()`），名称搜索/同组候选/单位表全靠它 |
| D3 | 投影层是本项目**真正的自研资产** | 引擎只给原始属性；"agent 能直接用"靠的是投影 |
| D4 | 计算链路上**没有 LLM** | 确定性优先；不可测的环节不进关键路径 |
| D5 | 多视角、无判据 | 场景未定，判据必然是伪权威 |
| D6 | 三态 provenance 强制 | 静默默认值是本类工具最大的错误来源 |
| D7 | 情景枚举（state × mode × overload）代替"假设一个状态" | 状态不可知但可枚举；一次 0.33ms，成本可忽略 |
| D8 | 知识层与计算层**物理隔离** | 知识会过时、会错；数值不能受它影响 |
| D9 | MCP 只吃结构化参数 | NL 由调用方 agent 承担（其本职），工具保持可复现 |
| D10 | 版本三元组写入每次输出 | SDE build / 引擎版本 / 规格版本，否则结论无法复现 |

## 7. 待确认项 → 已决

### 7.1 存储选型：**SQLite**

依据（实测规模）：

| 数据 | 量级 |
|---|---|
| types | 约 **54,000** |
| groups | 约 2,000 |
| dogmaAttributes | 2,871 |
| dogmaEffects | 3,427 |

五万行级别、查询模式简单（按名搜、按组列、按 ID 取），SQLite 零依赖（stdlib `sqlite3`）即可。
**DuckDB 留给战报层**（百万级 killmail 聚合，那时才需要列式）。

补充：索引库是**构建产物**，不入库（`.gitignore`），由构建脚本按 SDE build 号生成，保证可复现。

### 7.2 技能档推导位置：**L2 单一实现，L5 可覆盖**

- 推导逻辑只在 `Assumption Engine` 写一次（全 4 + 补最低），L5 只负责"传或不传"；
- 不传则用默认档，**并在 assumptions 里回显**；传了以传入为准，同样回显；
- 理由：若推导放在 L5，L3 投影层就不知道当前技能档，无法正确标 `assumed`——三态会失真。

### 7.3 情景清单：**改为「按需变体」，不设全局情景表**

实测引擎 `Environment` 只有三个字段：`damage_profile` / `security` / `reactive_armor`。

→ **以下原设想情景无法建模，必须从本期移除**：

| 原设想 | 结论 |
|---|---|
| `capped_out`（电容归零） | **不可建模**（引擎无电容状态输入）；只能近似为"关闭所有耗电模块"，且必须标注近似 |
| `webbed`（被网） | 属 `incoming.effects` 投影 → **对算接口**，不是单配装情景 |
| `no_ammo` | 可用 charge 置空近似，意义有限，降为细节 |

**新方案**：本期不维护全局 `scenarios.yaml`，改为：

- 每个视角**声明自己需要的变体**（机动要"推进 off/active/overload"、火力要"overload off/on"、不稳定要"逐模块关闭"）；
- `Scenario Runner` 合并去重、按 `(fit_hash, variant_key)` 缓存后批量计算（单次 0.33 ms，量级可忽略）；
- 真正的「情景矩阵」留给**对算接口 / 战报层**——那是为了解释"这场为什么输"。

**已确认可建模的维度**：

| 维度 | 支持方式 |
|---|---|
| 模块状态 | `state` ∈ `offline / online / active / overload` |
| 模式（T3D/T3C） | `ship.mode = <type_id>` ✓ 已确认 |
| 过载 | `state="overload"` |
| 伤害剖面 | `environment.damage_profile` |
| 安全等级 | `environment.security` |
| 反应式装甲 | `environment.reactive_armor` |

**槽位枚举（权威值，实测报错信息给出）**：`high / medium / low / rig / subsystem / service / fighter_tube / fighter_bay / implant / booster / drone_bay / cargo`。

**模式（T3D/T3C）的枚举来源 —— 已查清**：

- 模式**不是船的属性，而是独立的 type**，全部在 **group 1306**（本组内类型为 `published=false`）；
- Hecate 实测：`35686 Hecate Defense Mode` / `35687 Propulsion Mode` / `35688 Sharpshooter Mode`；
- 模式 type 自带的属性就是模式修饰项，例如 Defense 模式：

| 属性 | ID | 值 |
|---|---|---|
| `modeEmResistancePostDiv` | 1997 | 1.5 |
| `modeExplosiveResistancePostDiv` | 1998 | 1.5 |
| `modeThermicResistancePostDiv` | 1999 | 1.5 |
| `modeKineticResistancePostDiv` | 2000 | 1.5 |
| `modeArmorRepDurationPostDiv` | 2030 | 1.5 |

- **没有"船 → 可用模式"的显式链接属性**（模式 type 只有 volume / mass / hp / techLevel / meta + 模式修饰项），只能靠 **group 1306 全表 + 命名约定 `<ShipName> <Mode> Mode`** 建映射。

> **由此得出一条硬架构约束**：ESI 对未发布类型完全不可见（`/universe/ids/` 名字检索 0 命中、`/universe/groups/1306/` 不返回成员）。
> → **索引库的主数据源必须是官方 SDE 文件**，ESI 只能作为补充（多语言名、按需详情），不能作为主源。

### 7.4 ×1000 缩放表：**只覆盖投影层实际用到的属性**

不追求覆盖全部 2,871 个属性——只对输出的 30–40 个字段建表，每个实测确认并写进单测。

已确认：`cycleTime` / `reloadTime` / `scanSpeed` / `shieldRechargeRate` / 武器 `speed` 为毫秒；`trackingSpeed` 与 `optimalSigRadius` 为 ×1000。

### 7.5 输出 token 预算：**P2 实测校准 + 预算护栏**

800–1500 token 是估计值，P2 用真实样本实测；加**预算护栏**：超阈值时自动降级（先截细节、再合并同类字段），而不是把大响应硬塞给调用方。

### 7.6 引擎升级风险：**锁版本 + 回归三件套 + 版本三元组**

引擎 13.x 为 Beta 且**随 SDE 每日重建发版**，"升级"是常态而非例外。

- 依赖 **pin 版本**，不自动升级；
- 升级流程：手动触发 → 跑回归 → 看 diff → 再决定；
- 回归三件套（脚本已在 `spike/`）：`verify.py`（抗性 vs ESI 基线 12/12）、`smoke3.py`（往返无损 + 单位/聚合）、`smoke2.py`（技能档与剖面敏感性）；
- 每次输出写版本三元组：`sde_build` / `engine_version` / `spec_version`。

### 7.7 剩余未决

| 项 | 说明 |
|---|---|
| `needs_implant` 判据 | **不收紧**：工程技能全 5 是玩家基础，判据照旧（全 5 档仍超载即提示） |
| 可疑点阈值 | **不设定绝对阈值**：快慢取决于同一场战斗里的其他人，属场景相对判断。工具只给数值，相对结论留给对算/战报层 |
| 模式的 `PostDiv` 语义 | 抗性 `PostDiv 1.5` 是"共振率 ÷ 1.5"，已由引擎结果反证正确，但需在单位/算子表里登记 |
